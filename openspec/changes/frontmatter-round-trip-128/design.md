## Context

`read_note` strips the YAML block and renders frontmatter as a formatted summary; `edit_note` default mode writes exactly `content`; section mode resolves headings over the **raw** file while `read_note` resolves them over the stripped body. `parse_frontmatter(raw)` returns `({}, raw)` for six distinct inputs, conflating "no frontmatter" (no line-1 fence) with "malformed frontmatter". `set_frontmatter` re-serializes whatever it got, so on the malformed cases it prepends a second block above the broken one and `remove=` no-ops; `serialize_frontmatter` already drops the block when the mapping empties.

Three Codex audit rounds shaped this design. Rounds 1–3 each broke a different attempt to *infer* whether incoming full-replace content was meant to carry frontmatter (line-1 fence → broken by thematic-break bodies; complete-valid-block → broken by a stripped body that itself begins with a mapping-shaped fenced block, which `read_note` legitimately produces). The conclusion is structural: **destructive intent cannot be inferred from content shape**. The design below asks for it explicitly.

## Goals / Non-Goals

**Goals:**
- The natural read-modify-write round trip can never delete frontmatter, for *any* body bytes — including bodies that begin with `---` or with complete mapping-shaped fenced blocks.
- Replacing or dropping frontmatter through `edit_note` requires explicit caller intent.
- Section mode cannot corrupt a frontmatter block, valid or defective, and selectors agree between `read_note` and `edit_note` wherever both operate.
- `set_frontmatter` refuses malformed blocks by name; removing the last key removes the block.

**Non-Goals:**
- No change to `read_note`'s response *shape* (its rendered header + content windowing). The one shared-parser correction (whitespace-only empty blocks recognized as frontmatter) does change what `parse_frontmatter` returns for exactly that input, for every consumer at once — see D3. No YAML comment preservation. No change to append mode (EOF) or find/replace mode (deliberately raw — the one mode that can intentionally edit frontmatter text in place).

## Decisions

**D1 — full-replace never touches an existing valid frontmatter block unless told to.** `edit_note` gains `replace_frontmatter: bool = False`, meaningful only in full-replace mode (supplying it with `append`/`find`/`section` is the existing multi-mode error shape).
- Default (`False`): when the file carries a valid line-1 block, the written file is `<existing raw block><separator><content>` — the block byte-identical, `content` the entire new body, whatever bytes it contains. No classification of `content` happens at all: a body starting with `---`, or with a complete mapping-shaped fenced block (exactly what `read_note` returns for a note whose body opens that way), is body.
- `replace_frontmatter=True`: the file is replaced wholesale with exactly `content` — today's behavior, now opt-in. This is also the escape hatch for deleting a block or repairing one wholesale.
- No valid existing block (absent or malformed): the default writes `content` wholesale (there is nothing valid to preserve; this keeps the repair path open without the flag).

**D2 — the separator is specified.** The preserved block slice is the parser's computed span (never `raw[:-len(body)]` — it fails on an empty body). When that slice does not end in a newline (a metadata-only note whose closing fence sits at EOF without one) and `content` is non-empty, one `\n` is inserted between block and body — outside the byte-identical claim, which covers the block bytes themselves. `---Body` corruption is impossible.

**D3 — the diagnosing parser pins the partition** (needed by `set_frontmatter` and section mode; full-replace no longer consumes it). `parse_frontmatter_diagnose(raw) -> (fm, body, defect)` with predicates identical to the read parser: opening fence = first line exactly `---` (trailing CR ok); closing fence = the parser's own `^---[ \t]*\r?$` (trailing spaces/tabs accepted — a block `read_note` strips is never diagnosed differently). Partition: *valid* = mapping, or whitespace-only fenced YAML (a valid empty mapping); *unclosed_fence* = line-1 fence with no closing fence, a bare unterminated `---` at EOF included; *yaml_error(msg)*; *not_a_mapping* = list, scalar, or non-whitespace YAML loading to `None` (`null`, `~`, comment-only — comment-only must not be valid, or its `#` line would break read/write section parity); *absent* = everything else (`----`, `--- x`, leading content, no fence). The whitespace-only-empty-block correction SHALL land in `parse_frontmatter` itself — not only in the diagnosing sibling — so every consumer (read, index, diagnose) shares one partition: leaving the read parser treating `---\n---\n` as absent while the write side preserves it as a valid block makes the read-body → default-edit round trip *duplicate* the block (round-4 blocker). This is the one deliberate behavior change to `parse_frontmatter` **as designed**; every other branch was untouched. A later adversarial round added a second, for the same reason as the first: the read path resolves a file through universal-newline translation before parsing, so a lone-CR note's block was recognized and stripped on read while the raw-byte write paths, splitting on `\n` alone, diagnosed the identical bytes as *absent* — default full-replace deleted the block the round trip advertises it preserves, and `set_frontmatter` prepended a second one. The partition therefore ends a line at LF, CRLF or a lone CR, and the ATX heading scan takes the same rule: fixing the partition alone converts section mode's safe "no ATX headings" refusal on such a note into a write against a bogus heading spanning the rest of the file, because `.` matches `\r`. For notes already indexed under the old partition (an empty block surfacing as literal body text), the index does NOT self-heal on an ordinary pass — change detection hashes the raw bytes before parsing, and unchanged bytes skip the reparse. This staleness is **accepted and declared**: such notes are vanishingly rare, the stale artifact is cosmetic (a literal `---` pair in indexed body text), and it heals on the note's next hash-changing content edit, or under the explicit per-index recovery operations — `make rebuild-tsvectors` for the keyword vector, reset/re-embed for embeddings, a provenance re-derive for metadata — none of which an ordinary reindex performs (unchanged hashes are skipped). Stored `note_links.position` values for such notes are similarly stale (measured against the unstripped content) — the same cosmetic class, repaired by the same operations. A parser-revision invalidation mechanism is not worth building for it.

**D4 — composition ordering.** Composition (block + separator + content) happens first; the size cap applies to the composed result; `expected=` keeps comparing the complete raw file bytes (a concurrent frontmatter-only change conflicts); `dry_run` diffs the composed result.

**D5 — section mode: body-resolution over a valid block, refusal over a defective one.** With a valid line-1 block, heading resolution (all three selector forms), replacement, and the not-found/ambiguity listings operate on the frontmatter-stripped body — the text `read_note` scans — and the write reattaches the raw block byte-identically; a line inside the block (YAML `#` comments included) is never selectable and never counted by an ordinal. With a **defective** block (unclosed, YAML-error, non-mapping), section-mode writes are **refused**, naming the defect and pointing at `edit_note(replace_frontmatter=True)` as the repair — operating over raw there would let a `#` comment be selected as a heading and a replacement delete the closing fence (round-3 blocker). With no fence at all (absent), raw is the body and resolution proceeds as today. The read side deliberately keeps extracting from malformed-block notes (reads destroy nothing); the asymmetry is stated in the docstrings.

**D6 — `set_frontmatter` refuses on any defect, and only an *effective* mutation reaches the serializer.** A call whose `updates` change no value (compared type-sensitively — `True` vs `1` IS a change; plain `==` conflates them) and whose `remove` names no present key returns a byte-identical no-op before serialization — the guard that keeps a remove-of-nothing from dropping a valid empty block (which would promote a mapping-shaped body prefix into active frontmatter). Block removal happens only when an actual last key was removed. Otherwise: it refuses on any defect, naming it (with the parser's message where there is one) and pointing at `edit_note(replace_frontmatter=True)` as the repair; `remove=` refuses identically. The empty fenced block is valid input. Removing the last key leaves no block at all — fences, YAML region and separator gone, body exactly as it was (current serializer behavior, made normative).

**D7 — the contract lives where agents read it.** The registered wrapper docstrings in `src/mcp_server/server.py` are what MCP clients see; they and the `tools.py` impl docstrings both state the new contract (the current registered `edit_note` text says full replacement overwrites the entire file, which becomes false by default).

## Risks / Trade-offs

- A new optional parameter on `edit_note` (`replace_frontmatter`) — additive, default preserves; existing callers that relied on body-only full-replace deleting frontmatter get preservation instead, which is the fix.
- Section-mode writes on malformed-block notes are refused where they previously "worked" by corrupting the block silently; the refusal names the repair.
- Section-mode ordinals shift for notes whose frontmatter contains `#`-comment lines (previously counted as headings on the write side): this is the parity fix.
- No BOM policy is needed for incoming content (nothing is classified); a BOM'd payload under `replace_frontmatter=True` is written as given — explicit intent.
