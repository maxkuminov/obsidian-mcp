## Why

Three findings from the 2026-09-04 OWASP ASVS 5.0 assessment sit on the same surface — the panel's browser session and the consent screen it authorizes grants from — and each one ends at the same place: an attacker holding a panel cookie can mint `readwrite` `omcp_` API keys and approve OAuth grants against a tenant's vault, which is durable agent write access to Max's source of truth.

**#198 (V7.4.1) — logout does not log you out.** `logout()` calls `request.session.clear()` and nothing else (`src/auth/routes.py:204-206`). Starlette's `SessionMiddleware` answers that with an expiring `Set-Cookie`; the cookie that was already issued stays a valid, correctly-signed credential until its itsdangerous timestamp passes `session_max_age` — seven days. The verification on the issue replayed a pre-logout cookie against the container's installed Starlette 1.6.0 and got `user_id 7` back after the user had signed out. The only server-side invalidator in the tree is `users.session_version` (`src/auth/session.py:151`), and exactly one handler increments it: the admin password reset (`src/control_panel/users.py:610`). No test in `tests/` references logout at all.

**#197 (V6.2.2) — no way to rotate your own password.** Every route that writes `password_hash` outside bootstrap is on the admin router (`src/control_panel/users.py:55`, `:579-613`). In production `multi_user_mode` a non-admin who suspects their password is compromised has to ask an administrator, who then knows the replacement. `README.md` states the gap as a design position ("Password reset is admin-driven only"), which is why it was never treated as a bug.

**#183 (V10.4.7) — the consent screen cannot tell you who is asking.** `/register` is unauthenticated, so every OAuth client on this server is self-registered, and `_valid_redirect_uri` checks only "https, has a host, no fragment" (`src/oauth/routes.py:61-66`). `authorize_get` passes `client_name` — attacker-chosen text — and no redirect host, no client identifier, no registration date and no trust statement (`:396-411`). A client named "Claude" with a redirect to an attacker's host renders a page indistinguishable from the real connector's. `/authorize` sits behind `chain-oauth@file`, so the reachable victims are exactly the Google-authorized panel users, i.e. the population that holds vaults. The read-only preselect (#63) caps the default at read, which for a multi-tenant vault of record is still full exfiltration.

The three are one change because they are one flow: a session that cannot be ended is the credential a phishing consent screen is redeemed with, and self-service rotation is useless if rotating the password leaves the stolen session alive.

## What Changes

- **A server-side session registry.** A new `user_sessions` table (migration **024**) holds one row per live browser session: `id` (the **SHA-256 of** a 256-bit CSPRNG identifier), `user_id`, `created_at`, `last_seen_at`, `expires_at`, `revoked_at`, `user_agent_hash`. The signed cookie carries the identifier alongside the fields it already carries; `get_active_session_user` resolves the row and refuses a cookie whose row is missing, revoked, or expired, on top of the existing user-exists / user-active / `session_version` checks. The cookie transport does not change — Starlette's `SessionMiddleware` stays, because `verify_csrf` depends on it in both modes.
- **Logout revokes the row.** `POST /admin/auth/logout` stamps `revoked_at` for its own session before clearing the cookie, so the replay the issue demonstrated answers 302 to login. A revocation that fails — or a rollback that fails after it — still clears the cookie and redirects, recording an ERROR that carries the exception's **class name only**: refusing the sign-out would leave the user signed in *and* the cookie alive, and SQLAlchemy renders bound parameters (here, the stored session hash) into an exception's text.
- **The mint runs inside the account guard and commits there; the revoke helpers never commit.** `start_session` takes the same advisory key the administrative handlers take, re-reads the account `FOR UPDATE` with `populate_existing=True`, requires it to exist and be active, inserts, and commits — all in one critical section. Committing matters because `get_session` neither commits nor rolls back, so an insert left to a caller's discretion may never happen and the cookie beside it would authenticate nothing. Holding the guard matters because a mint that runs after the guard is released can be overtaken by a deactivation and will then create a **live row for a just-disabled account** — refused while the account is inactive, which hides it, and a working credential the day it is reactivated. The revocation helpers deliberately do not commit, because they must ride the critical section their callers hold. The last-seen touch runs **on the request's own session**, on safe methods only, committed inside the dependency: a second `AsyncSession` would hold two connection-pool leases per request against a pool that tops out at fifteen.
- **Every account-level event revokes the user's other sessions**, in the same transaction as the write that makes it true and inside the `_lock_admin_guard` critical section where one is held: admin password reset, deactivation through the user edit form, and the soft delete. A permanent delete needs no code — the rows carry `ON DELETE CASCADE`.
- **`POST /admin/account/password`, self-service.** A new non-admin panel page (`GET /admin/account`) and handler taking `current_password`, `new_password` and `new_password_confirm`, CSRF-protected by the panel router's existing dependency, verifying and hashing through the existing `verify_password` / `hash_password` — **the 72-byte truncation and the NUL rejection are preserved exactly; they are not bugs to fix.** On success it writes the hash, increments `session_version`, revokes **every** session of that user, and immediately mints a fresh one for the browser that made the request. Net user-visible effect: other devices are signed out, this one is not. The admin reset stays as the recovery path.
- **The change verifies and writes under the account guard, against a re-read row.** The handler takes the *same* advisory key `_lock_admin_guard` uses, re-reads the acting user `FOR UPDATE` with `populate_existing=True`, and re-checks `is_active` before verifying anything. Verifying against the `User` a FastAPI dependency loaded is how a concurrent administrator reset gets silently overwritten — the change would be authorised by a hash the administrator has already replaced, restoring access they had just removed. The key moves to `src/oauth/grants.py`, which already owns this codebase's advisory-lock primitives, with its **value unchanged**.
- **The change-password route carries two independent throttles** at the login rate: one keyed on the authenticated account, one on the client address. Neither subsumes the other — an account-only key lets one address walk many accounts, and any key mixing the address in hands an attacker a fresh allowance per address, which is why a single composite key does not bound guessing against one account.
- **One password policy, one constant.** `MIN_PASSWORD_LENGTH = 12` in `src/auth/passwords.py`, applied by **four** setters — the new handler, the bootstrap form, the admin reset and the admin `create_user`, the last three at 8 today. All four also route through a shared validator that turns an embedded NUL into a form error: `hash_password` raises on one, so each is a latent 500 today. No composition rules, no maximum below bcrypt's own truncation, and no forced rotation: existing accounts are never re-checked at login.
- **The consent card identifies the client.** `authorize_get` additionally passes the redirect URI's **host** (from `urlparse(...).hostname` — never `netloc`, so `https://claude.ai@evil.example/cb` correctly reads `evil.example`), the `client_id`, and the client's registration date. A standing notice on **every** render says the application registered itself and is not verified by this server.
- **Registration stops accepting hostless and non-ASCII redirect URIs.** `_valid_redirect_uri` checks only the scheme, a truthy authority and the absence of a fragment, so `https://@/cb` registers — authority `"@"`, host empty — and would render a consent card with no destination at all. Registration now requires a non-empty host and a successful IDNA-to-ASCII conversion, storing the converted form. Rows registered earlier may still carry an empty or non-ASCII host, so the display path degrades explicitly ("destination could not be determined") and always takes the warning branch.
- **An operator-configurable allow-list of known connector redirect hosts** (`OAUTH_KNOWN_REDIRECT_HOSTS`, default `claude.ai,chatgpt.com`) drives a "known client" badge; every other host gets the stronger warning naming the host the authorization code would be sent to. Matching is **exact host equality**, lower-cased ASCII: no suffix match, no wildcard, so `evilclaude.ai` and `claude.ai.evil.example` are unverified. An empty list means everything is unverified, which is the safe direction.
- **Expired session rows are purged by the existing cleanup job**, retained until seven days past the **later** of `expires_at` and `revoked_at`. The OAuth half's `expires_at`-only rule does not transfer: an administrative reset revokes every unrevoked row of that user *including already-expired ones*, and such a row is immediately past its expiry, so the next tick would delete the record of a revocation an operator performed minutes earlier — the #64 blank space, reintroduced.
- **Configuration bounds are enforced.** `SESSION_TOUCH_INTERVAL_SECONDS` and `SESSION_PURGE_RETAIN_DAYS` are both `ge=1`: a zero touch interval turns a throttled hint into a write on every request, and a zero retention window deletes a revocation the moment it is made.
- **Security events are declared in the shared catalogue, not emitted past it.** `src/services/security_events.py` gains `panel_session_replay_refused`, `panel_sessions_revoked`, `panel_password_changed` and `panel_password_change_refused` in `EVENT_FIELDS` (`panel_logout` is already there), using only fields that change's `ALLOWED_FIELDS` already declares. **No credential material is ever recorded** — not the session identifier, **not its stored SHA-256** (the registry's key, and therefore the name of a specific live session), not a password, not a hash, and no substring of any of them twelve characters or longer. Where a session must be identified it is by `token_tag`.

Migration 024 creates one table and backfills nothing. No new dependency.

## Dependencies on sibling changes

**`security-event-logging` (PR #216)** owns the event catalogue, the `ALLOWED_FIELDS` allow-list and the `security_events.emit` contract. Its proposal has merged and its Slice A is being implemented, so this change **assumes `src/services/security_events.py` exists** and declares its four new events there. Because that file is a shared surface two changes are editing at once, exactly one slice here owns it (slice 7), sequenced after the sibling's Slice A. The fields used — `reason`, `user_id`, `username`, `count`, `route`, `method`, `client_ip`, `token_tag` — are all already in that allow-list; none is added. If the module turns out to be absent at merge time, the same names go through `logging.getLogger(__name__)` with the identifiers in the **message text** (the deployed formatter is `%(message)s`), and the substitution later is mechanical.

**`index-integrity-hardening`** owns migration **023**. 024's `down_revision` is `"023"`, so 024 MUST NOT merge or migrate ahead of it; if 023 is abandoned, 024 is rebased onto the then-current head before merge and the `schema-integrity` delta updated. `tests/integration/test_schema_check.py`'s `HEAD_REVISION` moves to `"024"` only once both are in — and that move is written as a **modification** of the existing head requirement, not a second requirement beside it.

## Capabilities

### New Capabilities

- `panel-session-registry`: the browser session becomes a server-side row with a lifecycle — minted at login, validated on every request, touched, revoked by logout and by every account-level event, and purged on the OAuth retention schedule. A signed cookie is no longer sufficient on its own.
- `panel-account-password`: a signed-in user can change their own password, under CSRF and a per-(IP, account) throttle, with the effect on their other sessions specified.

### Modified Capabilities

- `oauth-authorization-integrity`: consent revalidation now runs through the session registry as well as `session_version`; the consent screen must identify the requesting client — redirect host, client identifier, registration date, an unconditional self-registration notice, and a badge or a warning decided by the operator's allow-list; and client registration must require a redirect URI with a resolvable ASCII host.
- `panel-user-administration`: the admin actions that end an account's access (password reset, deactivation, both deletes) must end its live sessions too, in the same transaction as the write.
- `schema-integrity`: migration 024 owns `user_sessions` as a marked unit that reconciles or refuses; the existing schema-gate head requirement is **modified** to move from `017` to `024` and to state the ordering against 023.

## Review

Two pre-code Codex rounds have run against this proposal and both returned FAIL. **Round 1** (3 BLOCKER, 11 MAJOR, 3 MINOR): a password change verifying and writing against a dependency-loaded row with no locked re-read; a mint inserting a row nobody was required to commit; and a last-seen touch taking a second connection-pool lease per request. **Round 2** (1 BLOCKER, 1 MAJOR, 2 MINOR, round 1 accepted as resolved): round 1's own answer to the mint — commit, but *after* the guard was released and with no fresh active-account check — left a window in which an administrator's deactivation is followed by a mint creating a live row for the account just disabled, invisible until the account is reactivated. All twenty-one findings are folded in; none rejected. Both maps from finding to decision are the last two sections of `design.md`.

## Impact

- `src/models/db.py` — new `UserSession` model; `User` gains a `sessions` relationship with `passive_deletes=True` and a delete cascade, so `session.delete(user)` relies on the database's own `ON DELETE CASCADE` rather than loading and deleting each row. `alembic/versions/024_user_sessions.py` — marker-owned in the shape 016/017/022 established: a `COMMENT ON TABLE` marker mirrored in the model, exact reconciliation that **refuses** a foreign or partial same-named table rather than patching it, a marker-guarded downgrade, rows preserved across a stamp-back re-run, and no backfill on any path.
- `src/config.py` — `session_touch_interval_seconds` and `session_purge_retain_days` (both `ge=1`), and `oauth_known_redirect_hosts` (with the `NoDecode` + CSV/JSON validator `fts_configs` uses; a bare `list[str]` is JSON-decoded by pydantic-settings and a comma-separated env value would fail).
