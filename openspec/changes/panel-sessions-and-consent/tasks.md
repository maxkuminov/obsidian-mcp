## 2. Session lifecycle — mint, validate, touch, revoke

- [ ] 2.1 `src/auth/session.py`: `start_session(request, session, user)` — `sid = secrets.token_urlsafe(32)`, insert the row keyed on `sha256(sid).hexdigest()` with `expires_at = now + settings.session_max_age` and `user_agent_hash = sha256(user-agent)`, then write `sid` into the signed cookie beside the existing `user_id` / `session_version` / `is_admin` / `username`. **One implementation, three callers.**
- [ ] 2.2 Same module: `revoke_session(session, sid_hash)` and `revoke_user_sessions(session, user_id)` — both `UPDATE … SET revoked_at = now() WHERE … AND revoked_at IS NULL`, issued on the **caller's** `AsyncSession`, **neither commits**. The caller commits. This is what keeps `_lock_admin_guard`'s check-then-act atomic (`docs/architecture/control-panel.md`, "The last-admin guard"): nothing may commit between the lock and the protected write.
- [ ] 2.3 Same module: `touch_session(sid_hash)` — updates `last_seen_at` only when the stored value is older than `settings.session_touch_interval_seconds`, in its **own** `async_session()` which it commits itself, and swallows + logs any failure. Not the request's session: a dependency writing there would put the touch inside the handler's transaction, lose it on a rollback, and share a transaction with the admin critical section.
- [ ] 2.4 `get_active_session_user`: require **both** `user_id` and `sid` in the cookie — a cookie with no `sid` is a pre-deploy cookie and is **refused, not grandfathered**. Then, in order: resolve the row by `sha256(sid)`; refuse when absent, when `revoked_at` is set, when `expires_at <= now`; then the existing user-exists / `is_active` / `session_version` checks, which stay. Every refusal keeps calling `request.session.clear()`. On success, call `touch_session`.
- [ ] 2.5 `src/auth/routes.py`: `login_submit` and `register_submit` mint through `start_session` instead of writing `user_id` / `session_version` by hand. Keep the `request.session.clear()` that precedes them.
- [ ] 2.6 `src/auth/routes.py`: `logout` gains `session: AsyncSession = Depends(get_session)`, reads the `sid` **before** clearing, revokes that one row, commits, clears, redirects. On a raised revocation: roll back, record ERROR, **still clear the cookie and still redirect** — a 500 on the sign-out button leaves the user signed in *and* the cookie live.
- [ ] 2.7 `src/auth/routes.py`: `login_form` stops reading `request.session.get("user_id")` directly (`:150`) and resolves through `get_active_session_user`. Without this a revoked cookie bounces between the login page and `/admin/` forever.
- [ ] 2.8 Records, using the sibling catalogue's names (see the design's D16): `panel_session_replay_refused`, `panel_sessions_revoked`, plus the existing `panel_logout`. **Never** the session identifier, a password or a hash — where a session must be named, use the catalogue's `token_tag` form. If `src/services/security_events.py` exists in the merged tree, emit through it; otherwise a module logger with the identifiers **in the message text** (the deployed formatter is `%(message)s`).
- [ ] 2.9 `tests/test_issue_198_session_registry.py`: the regression the issue asks for — sign in, capture the cookie, log out, **replay the pre-logout cookie → 302 to login** — plus: a cookie with no `sid` is refused; an expired row is refused while its signature is still valid; a revoked row is refused; a live row authenticates; a second session survives the first one's logout; `login_form` renders the form for a revoked cookie instead of redirecting; the touch is skipped inside the interval and issued outside it; a raising touch still serves the page; a failing logout revocation still clears and redirects; no record contains the identifier or any ≥12-character substring of it.
- [ ] 2.10 Confirm the new module **fails against the pre-change handlers** and passes after.

## 3. Revocation call sites and the purge

- [ ] 3.1 `src/control_panel/users.py` `reset_password`: after the hash write and the `session_version` bump and **before** the existing `await session.commit()`, call `revoke_user_sessions(session, target.id)`. Add no commit — the `_lock_admin_guard` advisory lock is held and the guard's atomicity depends on that.
- [ ] 3.2 `edit_user_submit`: when the write clears `is_active` for the target (`new_active` false and the target was active), revoke the target's sessions in the same transaction, before its commit. Only on the deactivating transition; a vault-path edit revokes nothing.
- [ ] 3.3 `delete_user`: on the soft delete (`target.is_active = False`), revoke before the commit. On the permanent delete, add **nothing** — the `ON DELETE CASCADE` on `user_sessions.user_id` removes the rows, and a hand-written delete before `session.delete(target)` is redundant work that can only diverge.
- [ ] 3.4 Verify every refusal path still writes nothing: the last-administrator guard, the self-target refusal and the `_actor_still_privileged` re-check all return before the revocation.
- [ ] 3.5 Record `panel_sessions_revoked` with the reason (`admin_password_reset` | `user_deactivated` | `user_deleted`) and the row count, **after** the commit that makes it true.
- [ ] 3.6 `src/services/indexer.py` `cleanup_expired_tokens`: add `DELETE FROM user_sessions WHERE expires_at < now() - settings.session_purge_retain_days`. **Revoked rows are not deleted earlier** — the same rule and the same reason as the OAuth half (#64): a session can only be revoked while it exists, so a window measured from `expires_at` guarantees a revoked row stays readable for the full window afterwards, and a single comparison is therefore correct where an `or_` would not be. Extend the docstring and the summary log line; keep the function's name.
- [ ] 3.7 `tests/test_issue_198_session_revocation.py`: an admin reset revokes the target's rows and leaves the actor's alone; a deactivation revokes; a soft delete revokes; a permanent delete leaves no rows (cascade); a vault-path-only edit revokes nothing; each refusal path revokes nothing; a rolled-back transaction revokes nothing; re-revoking keeps the first revocation time. Purge: a row expired beyond the window is deleted, a just-revoked unexpired row survives, a live row is untouched.

## 5. Consent identity, allow-list, badge and warning

- [ ] 5.1 `src/oauth/trust.py` (new): `known_redirect_host(redirect_uri: str) -> bool` and `redirect_display_host(redirect_uri: str) -> str`. The display host is `urlparse(uri).hostname`, lower-cased — **`hostname`, never `netloc`**, so `https://claude.ai@evil.example/cb` reads `evil.example`. A non-ASCII host is returned in its punycode (`xn--`) form and is **never** decoded. Matching is case-insensitive **equality** against `settings.oauth_known_redirect_hosts` — no suffix, prefix, substring or wildcard: `evilclaude.ai` and `claude.ai.evil.example` must both be unknown. An empty list means nothing is known.
- [ ] 5.2 `src/oauth/routes.py` `authorize_get`: pass `redirect_host`, `client_registered_at` (`client.created_at`, date only) and `client_trust` (`"known"` / `"unverified"`) into the template context alongside the `client_id` it already passes. No change to `authorize_post` — it already re-validates the submitted `redirect_uri` against the registered list before minting, so the destination shown is the destination used.
