## Context
Live DB: `alembic_version` = 012; the nine columns are nullable; the CHECK from 010 is missing. 010's committed body created it, and Postgres DDL is transactional, so the live DB was either stamped past 010 or the constraint was dropped afterwards — the operator should audit deploy history/DDL privileges (#53), but 013 does not depend on the answer: it verifies and enforces the complete 010 shape. Measured 2026-08-15: 0 NULLs in every affected column, 0 rows violating the CHECK across 16 `oauth_clients`. Fresh throwaway DBs migrated 001→012 have the CHECK but the same nullability drift, so the nullability part is a migration bug, the CHECK part is live-only drift.

## Goals / Non-Goals
Goals: `alembic check` clean on fresh and live DBs; migration idempotent; never silently mutate/drop conflicting rows. Non-goals: changing model definitions; touching `transfer_tokens`.

## Decisions
1. **Backfill-then-SET NOT NULL per column, each guarded.** Use the model's server default for the backfill (`is_active`→true, `used`/`revoked`→false, `created_at`/`indexed_at`→`now()`); on the live DB this is a no-op. Idempotency: `ALTER COLUMN … SET NOT NULL` is idempotent in Postgres.
2. **CHECK constraint: lock, verify data, verify shape, then create/replace.** In the migration's transaction: `SET LOCAL lock_timeout = '10s'`; `LOCK TABLE oauth_clients IN SHARE ROW EXCLUSIVE MODE` (blocks DML, so the offender check cannot race a concurrent insert); `SELECT client_id FROM oauth_clients WHERE NOT (<predicate>)` → any → `raise RuntimeError` listing them (never `DELETE`/`UPDATE`); then resolve the constraint by `pg_constraint` on `conrelid = 'oauth_clients'::regclass AND contype = 'c' AND conname = …`: if absent → `ADD CONSTRAINT` and `COMMENT ON CONSTRAINT … IS 'created by 013_schema_reconciliation'`; if present, compare `pg_get_constraintdef` with the canonical predicate and require `convalidated` — a mismatch (e.g. a same-named `CHECK (true)`) → drop and re-add the exact predicate in the same transaction (data already verified), also commented; a matching validated constraint → no-op. Also verify the other effects 010 promised (`client_secret_hash` nullable; `token_endpoint_auth_method` varchar(32) NOT NULL default `client_secret_post`) and reconcile them the same way, so the whole 010 shape is guaranteed regardless of how the drift happened.
2a. **Nothing the CHECK reads is written before the CHECK has been verified.** The offender query runs over the *raw* rows, ahead of any reconciliation of `token_endpoint_auth_method`, and counts `token_endpoint_auth_method IS NULL` as an offender alongside `(<predicate>) IS DISTINCT FROM true`. A CHECK passes when its predicate evaluates to NULL, so on a database where the column was relaxed a row can genuinely hold a NULL method *and* a secret; backfilling that NULL to `client_secret_post` first — as the first draft did — would manufacture a passing row, i.e. invent an auth method for a client and let it authenticate with whatever secret it happens to carry. Only after the check passes does 013 touch the column's **type, default and NOT NULL** — declarative fixes that write no row value, and `SET NOT NULL` needs no backfill precisely because a NULL would already have raised. If the column is *absent* entirely (historically impossible: 010 always adds it) the migration refuses and tells the operator to apply 010's shape by hand, rather than stamping a guessed method onto every existing client.
2b. **The default is compared exactly, against the server's own rendering.** `pg_get_expr(adbin, adrelid)` from `pg_attrdef` versus a canonical default derived the same way as the constraintdef — set `DEFAULT 'client_secret_post'` on an empty `TEMP` table built `LIKE oauth_clients` (after the type has been reconciled, so the scratch column carries the canonical type) and read back what Postgres stored. A substring test (`'client_secret_post' in default_expr`) accepts `'not_client_secret_post'`, and `alembic check` does not compare server defaults at all, so an exact catalog comparison is the only thing standing between that drift and production.
3. **Downgrade** drops the CHECK only if it carries the 013 COMMENT marker (a fresh 001→013 database keeps 010's constraint); leaves NOT NULL. Both paths tested.
3a. **Locks/timeouts documented:** `SET NOT NULL` takes ACCESS EXCLUSIVE and scans the table (no rewrite); `SET LOCAL lock_timeout = '10s'` and `statement_timeout = '60s'` bound the migration so a long-lived transaction makes the deploy fail fast (old container keeps serving) instead of stalling; `usage_logs` (~10k rows) scans in milliseconds. Both are **per statement / per lock acquisition**, not a budget for the transaction as a whole — a migration of many fast statements can run well past 60s without tripping `statement_timeout`. `SET LOCAL` is scoped to the transaction and alembic runs every pending revision in **one** transaction (`env.py` does not set `transaction_per_migration`), so `upgrade()` ends with `RESET lock_timeout; RESET statement_timeout`; otherwise a future 014 inherits 013's bounds and blames its own SQL when a long index build trips them.
3b. **Lock order is child-first.** The five other tables (`api_keys`, `notes_metadata`, `oauth_codes`, `oauth_tokens`, `usage_logs`) are backfilled and set NOT NULL *before* `LOCK TABLE oauth_clients`, so the migration never holds the parent's lock while requesting a child's. That matches the application's own direction: the token exchange in `src/oauth/routes.py` takes `SELECT … FOR UPDATE` on `oauth_codes`, then reads `oauth_clients`, then inserts `oauth_tokens`. Same direction on both sides means a concurrent OAuth request **queues behind** the migration instead of closing a wait cycle with it. `oauth_clients.created_at` is the one column of the nine done after the lock, with the rest of the `oauth_clients` work; it is not an input to the CHECK. This is an ordering guarantee, **not** a promise of no contention: the residual behaviour under concurrent OAuth traffic is **rollback and retry** — a request already holding a lock the migration needs makes it wait, and past `lock_timeout` the migration aborts, the transaction rolls back whole, and the deploy fails before the container is recreated. Re-run it when traffic is quiet.
3c. **TEMP privilege.** `_canonical_constraintdef` and `_canonical_default` build scratch `TEMP` tables, so the migration role needs `TEMPORARY` on the database. The owner/superuser role the deploy uses has it; a locked-down migration role may not.
4. **Gate:** `alembic check` clean is necessary but not sufficient (autogenerate does not compare CHECK predicates, and does not compare server defaults), so the integration test also asserts the catalog directly — `pg_constraint` row for `oauth_clients`, `contype='c'`, `convalidated`, `pg_get_constraintdef` equals the canonical predicate, and negative inserts (public client with a secret; confidential without) are rejected — plus the nine columns' `attnotnull` and `token_endpoint_auth_method`'s `attnotnull`/`format_type`/`pg_attrdef` and `client_secret_hash`'s nullability. Idempotence is exercised by `alembic stamp 012` on the reconciled throwaway DB and `upgrade head` again (revision re-runs), not by a second `upgrade head`. Drift simulation: 001→012, drop the CHECK, drop NOT NULL on the nine, insert NULL rows where possible → 013 → assertions; a same-named `CHECK (true)` variant → replaced by the exact predicate; a violating-row variant and a NULL-method-with-secret variant → loud failure naming the client_id, catalog and rows unchanged; a dropped `token_endpoint_auth_method` → refusal; wrong default / wrong type / `client_secret_hash NOT NULL` / nullable method → reconciled, asserted in the catalog; downgrade on fresh (constraint kept) vs drifted (marker → dropped).
4a. **The gate has a command and cannot silently skip.** `make test-schema` starts a throwaway `pgvector/pgvector:pg16`, runs the module with `PGVECTOR_TEST_ADMIN_URL` and `OMCP_REQUIRE_SCHEMA_INTEGRATION=1`, and removes the container whether it passed or failed. The flag turns the opt-in skip into a hard failure: a gate that skips because nobody exported the URL is not a gate. It is the thing to run before any deploy carrying a migration.

## Risks / Trade-offs
- [Live rows violate the CHECK at deploy time] → migration fails loudly before altering anything; deploy aborts (make deploy migrates before recreating the container, so the old container keeps serving). Measured 0 today.
- [SET NOT NULL locks the table] → tables are small; `usage_logs` is the largest (~10k rows) — sub-second.
- [autogenerate still noisy for other reasons] → the test tells us.

## Migration Plan
`make deploy` (migrate step). Post-deploy: `docker exec obsidian-mcp alembic check` → "No new upgrade operations detected."; `pg_constraint` shows the CHECK. Rollback: `alembic downgrade 012` (drops CHECK only).
