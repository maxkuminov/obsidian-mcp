## Context
`validate_path` returns `(vault/rel).resolve()`; `validate_visible_path` adds the dot-dir check on the resolved relative path. Every write then uses that resolved `Path`, so a symlink is transparently followed. `delete_file` (#50) instead canonicalises lexically and walks with `O_NOFOLLOW`. Migrating all note writes to the anchored helper is the long-term follow-up recorded in CLAUDE.md; this change is the minimal, safe step: refuse the one dangerous shape.

## Goals / Non-Goals
Goals: no mutating tool can act on a file other than the one named; symlinked directories inside the vault keep working; clear error messages. Non-goals: anchored (`dir_fd`) rewrite of `_atomic_write`; changing read behaviour; symlink support policy for the indexer.

## Decisions
1. **Refuse symlinked final component; allow symlinked ancestors that resolve inside the vault.** Refusing ancestors would break shared-attachment-folder setups; the data-loss vector is the final component (act on B while naming A). Ancestor links resolving *outside* the vault are already rejected by containment.
2. **Resolve the parent, refuse a symlinked final component, operate on `resolved_parent / name`.** `validate_mutable_path` normalises `rel` with `PurePosixPath` (reject `..`, absolute, NUL, empty, trailing slash), resolves the *parent* directory (`(vault/rel).parent.resolve()`, must be inside `vault.resolve()` — this is where in-vault symlinked ancestors are allowed and escaping ones rejected), `os.lstat`s `resolved_parent / name` (`S_ISLNK` → refuse, naming the canonical vault-relative target when it resolves inside the vault, else "outside the vault"), applies the hidden-path check to the resolved relative path, and returns `resolved_parent / name`. Consequences: (a) the filesystem operation happens on the real directory entry the indexer sees, so the DB path (`notes_metadata.file_path`, `note_links`) — which the indexer stores as the *resolved* relative path for files under symlinked directories — matches what `move_note` reads/writes: `move_note` derives `from_rel`/`to_rel` from the returned paths relative to the vault root; (b) an allowed symlinked ancestor is traversed once, at validation, and never re-traversed during the mutation, so repointing it afterwards cannot redirect the write (the residual TOCTOU is only the final-component swap, same class as today's optimistic writes — documented, and closed later by the anchored-helper migration); (c) `_atomic_write` receives a real directory for its temp file.
3. **Error text names the target**: `"alias.md is a symbolic link to important.md — mutating tools act only on the named file; operate on the target instead."`
4. **Dangling symlink at a destination** (create/write/move-to): refuse (it is a symlink) — no write.
5. **`move_note` destination:** refuse if the destination's final component is a symlink (existing no-clobber would otherwise fail on the link name anyway, but message clarity matters); source symlink refused.
6. **Reads unchanged** — documented; `read_note` of an alias returns the target's content as before.

## Risks / Trade-offs
- [Users who edit through aliases lose that ability] → they get a message naming the real path; safer than silent retargeting.
- [DB paths vs symlinked directories] → the indexer stores files under symlinked directories at their resolved path (`os.walk` does not follow directory links, so they are seen via the real directory); operating on `resolved_parent / name` keeps `notes_metadata`/`note_links` and `rewrite_links` backlink discovery consistent — covered by an integration-style test with an indexed note under a symlinked folder moved through the link.
- [TOCTOU: final component swapped for a link after lstat] → same optimistic level as today's note writes; ancestor repointing after validation cannot redirect (resolved parent is used); documented as accepted; the anchored-helper migration closes it later.
- [Accepted residual, stated precisely] → a *static* alias anywhere in the vault (the #54 vector) can no longer redirect any mutation; what remains is a live race, where a concurrent process renames the resolved parent directory (leaving a symlink at its name) or repoints a symlinked vault root *between two syscalls of a single write or soft-delete*. Closing that needs the descriptor-anchored migration tracked in issue #59; until then it is accepted, and it requires write access to the vault's own directories at exactly the wrong instant.
- [Temp-file staging] → `_atomic_write` creates its `.tmp-…` file with `O_CREAT|O_EXCL|O_NOFOLLOW` (mode 0600, relaxed to the umask default before publication so note permissions are unchanged) and retries the name a few times, so a guessed temp name pre-created as a symlink is an `EEXIST` we step around rather than a decoy the staged write truncates.
- [`vault_fs` reuse] → not adopted wholesale here because it refuses symlinked ancestors, which this change deliberately allows.

## Migration Plan
Deploy; post-deploy e2e via live tools: create a symlink in a scratch folder on the host, `edit_note`/`delete_note`/`set_frontmatter`/`write_file` on it → refused, target byte-identical; `read_note` still works; a symlinked scratch dir inside the vault still accepts `create_note`.
