## Context

Five verified defects (#127) in the index/search layer. Shared background: the embed pass selects rows on `embedded_content_hash IS NULL OR != content_hash` and certifies through `certify_embedded(id, content_hash, file_path)` (a conditional row-locking UPDATE); the keyword index is one tsvector column written per changed note inside the pass transaction; every index pass runs under `index_pass_lock`; PostgreSQL rejects a tsvector larger than 1 MiB, and an uncaught error aborts the whole pass transaction so nothing commits and the same batch retries every tick (the #126 freeze class).

A Codex pre-implementation audit (FAIL, 3 blockers) reshaped this design; the deltas below are the post-audit shape.

## Goals / Non-Goals

**Goals:**
- An ownerless read never crosses a tenant boundary: `user_id=None` reads exactly the `user_id IS NULL` rows on **every** index-backed tool — search, list, recent, tags, and every graph traversal — with graph edges closed over the owned note set.
- Editing `EMBEDDING_EXCLUDE_PATTERNS` converges: after one *completed* embed pass, vectors exist iff the current config includes the note, for every row whose certification is current and whose content embeds successfully.
- A move (either path) leaves `title` exactly what a fresh index of the file would produce, derived by the same shared helper over the file's current bytes.
- Keyword indexing attempts full content and degrades per-note without aborting a pass or stranding stale state.
- A note with many chunks eventually embeds completely; certification requires full chunk coverage; a hung provider still times out.

**Non-Goals:**
- No persistent-failure quarantine for notes whose embedding fails for non-timeout reasons (pre-existing behavior, unchanged).
- No re-chunking or provider protocol changes; no schema migration.
- No change to `read_note` (derives its title from the filesystem, already correct).

## Decisions

**D1 — read scoping: `None` maps to `IS NULL`, totally, and graph queries are closed over the owned set.** `apply_note_filters`'s `user_id=None` semantics change from "no predicate" to `user_id IS NULL` — the write path's `_note_owner_predicate` mapping. The sweep enumerates every index-backed tool: `keyword_search`, `semantic_search`, `list_notes`, `get_recent`, **`get_tags`**, `get_backlinks`, `get_links`, `get_neighborhood`, `find_related`, `find_orphans`. For the graph tools, replacing `if user_id is not None` branches is not sufficient: any join through `note_links.target_note_id` or `source_note_id` that can surface another row's title/path — or let a cross-owner edge influence membership (neighborhood BFS, orphan calculus) — must require **both endpoints** inside the owned note set (dangling links keep their rows; the ownership predicate rides the JOIN, not a post-filter that drops them). Single-user deployments see no behavior change (all rows NULL-owned). The alternative — refusing `None` reads when multi-user rows exist — was rejected: `MULTI_USER_MODE` off with legacy multi-user rows is a legitimate operator state, and the NULL slice is exactly what a single-user credential owns.

**D1a — the owner predicate counts as a filter for the exact zero-row fallback.** With scoping total, every HNSW query is a *filtered* query; `semantic_search`/`find_related` currently enable the zero-row exact fallback only when `user_id is not None` or another filter is present, so an ownerless mixed-database query could return empty while NULL-owned matches exist. The fallback eligibility becomes unconditional: any zero-row vector result re-runs exact.

**D2 — exclusion reconciliation is a per-pass sweep over *certification-current* rows, reusing the certified stamp-then-delete discipline.** After the normal backlog, the pass selects rows where `embedded_content_hash IS NOT DISTINCT FROM content_hash` (owner-scoped) with `EXISTS(note_embeddings)` as `has_vectors`, and evaluates the current patterns in Python (~2.5k rows; fnmatch is Python-side by design):
- *excluded and has_vectors* → the existing exclusion branch verbatim: `certify_embedded(id, content_hash, file_path)` then `DELETE` vectors, per-note commit. Never delete-by-id — a concurrent move must make the stamp miss and roll the note back.
- *included and no vectors* → the stamp may be a stale exclusion stamp or a legitimate zero-chunk note. Read the bytes beneath the pass's pinned root; on hash mismatch skip (the ordinary backlog owns that row next pass); clean + chunk; zero chunks → write nothing (the row is already correct: current certification, zero vectors); else embed through the existing `embed_note` certified path.

**Convergence is defined for a *completed* sweep**: after a reconciliation sweep that visited every selected row without pause or error, every row whose certification is current satisfies "has vectors iff included by the current config", except rows whose content cleans to zero chunks (correct with zero vectors), rows whose bytes no longer hash to the row (owned by the backlog next pass), and rows whose provider call failed (unstamped where the stamp would be new, retried next pass). A pause mid-sweep stops between notes and the next pass runs a fresh, idempotent sweep from the start — per-note commits make replays no-ops. The cost of the "included, no vectors" probe is one file read per genuinely-empty note per pass — bounded, accepted.

**D2a — this modifies the base embedding-pass requirement.** The base `index-integrity` requirement ends by asserting the pass "still selects only rows whose `embedded_content_hash` differs from their `content_hash`". The delta therefore ships as a MODIFIED requirement defining two explicit eligibility sets: the hash-mismatch backlog (unchanged semantics) and the certification-current reconciliation sweep (new), with everything else about that requirement intact.

**D3 — move title: exact parity via the shared derivation, reading the file.** `_note_title(frontmatter, filename)` (the #126 helper) is the single definition of title derivation. The indexer's move path binds `title = :title` from the parsed new-path entry it already holds — exact by construction. `move_note`, after its move commits and the inode is verified, reads the moved note through the destination target's descriptor, parses frontmatter with the same `parse_frontmatter`, and computes `_note_title(fm, dest_name)` for the metadata UPDATE — parity with a fresh index including every falsy-title case (`false`, `0`, `[]`, `{}` all fall back to the new stem) and independent of stale indexed frontmatter. If the post-move read or parse fails (file vanished, undecodable), the UPDATE falls back to `_note_title(row.frontmatter, dest_name)` computed in Python from the row's sanitized JSONB — declared best-effort, self-healing at the next content change. The earlier SQL `CASE` on JSONB was rejected by audit: it disagreed with `_note_title` on falsy titles and trusted stale metadata.

**D4 — keyword index: full content first, savepoint-per-attempt, floor = today's statement, floor failure propagates.** One shared helper performs the tsvector UPDATE for both the incremental pass and `rebuild_tsvectors`: attempt the full body inside `async with session.begin_nested()` with the `try` **outside** the context manager, so a database error unwinds the savepoint via the context manager's own rollback before the next attempt — catching inside would leave the outer transaction aborted (audit finding). On failure, halve the content and retry (fresh savepoint per attempt) down to a floor of exactly 100,000 characters — **today's production statement**. A failure at the floor propagates and aborts the pass exactly as it does today: no new stale state is possible (the note's metadata upsert rolls back with the pass), no new freeze class is introduced (a floor statement that fails today also aborts today), and size-class failures cannot reach the floor (a 100,000-char input cannot exceed the 1 MiB tsvector limit). The skip-list escape hatch from the first draft is gone — audit showed it stranded a committed content_hash beside a stale vector, permanently. The two call sites carry different transactional guarantees and the spec states both: the **incremental pass** commits nothing on a floor failure, so the note is retried next tick; the **full rebuild** currently commits every 500 notes, which under a floor failure would strand a half-rebuilt keyword index that no periodic pass ever repairs (unchanged tsvectors are not re-selected) — so the rebuild becomes **atomic**: its intermediate commits are removed, a floor failure rolls the whole rebuild back, and the error surfaces to the operator who invoked it. Verification requires a **real PostgreSQL integration test** (the mocked-savepoint test cannot prove asyncpg's aborted-transaction state clears): trigger a genuine statement failure, observe the fallback succeed, run a later update in the same transaction, commit, verify both rows.

**D5 — the aggregate embed deadline is removed; the per-chunk bound is the timeout. Scope: OllamaProvider only.** The OpenAI provider keeps its own contract (60 s HTTP timeout, 3 attempts with backoff, native sub-batching) — it never had the aggregate-deadline defect. `OllamaProvider.embed_batch` drops its fixed 300 s whole-batch deadline entirely and keeps the 30 s per-call `wait_for`. The aggregate could only ever fire when every chunk was individually healthy — i.e. exactly and only on the structurally-large-note bug — and any proportional replacement re-introduces a boundary where near-30 s chunks plus loop overhead exhaust it (audit finding). A hung provider still fails in ≤ 30 s. `embed_note`'s `len(embeddings) != len(chunks)` refusal is retained and specified: partial coverage is never certified. The pause flag is still only checked between notes; a giant note occupies the pass until it completes, once — accepted against the alternative (a permanent 300 s/tick retry that never completes).

## Risks / Trade-offs

- **D1** changes what an ownerless read returns on a mixed database from "everything" to "the NULL slice"; base note-filters scenarios that promised "identical to pre-change" behavior are re-scoped to all-NULL databases via MODIFIED requirements.
- **D1a** makes the exact O(n) fallback reachable from every zero-result semantic query; it remains the rare path (a genuinely-empty result on a populated slice).
- **D2** adds one bounded metadata query + Python fnmatch per embed pass; the "included, no vectors" probe re-reads genuinely-empty notes each pass.
- **D3** adds one file read per `move_note`; the JSONB fallback is declared best-effort for the narrow post-move-read-failure case.
- **D4**'s halving retreat can run the statement up to ~8 times for a pathological note, savepoint-isolated; in exchange ordinary notes are fully indexed for the first time and terminal behavior is exactly today's.
- **D5** allows a giant note to hold `index_pass_lock` for 30 s × chunks worst case, once. The panel pause takes effect at the next note boundary, as today.
