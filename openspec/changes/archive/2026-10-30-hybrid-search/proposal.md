Refs #354

## Why

`keyword_search` and `semantic_search` are distinct peers by design, and an agent that knows whether its query is an identifier or a paraphrase picks well. An agent that does not know has to guess, and often guesses wrong. The one measured pgvector + tsvector reciprocal-rank-fusion study (2026-10-22, 94 passages, 60 queries) puts numbers on it. Hit@1 was 41/60 vector-only, 36/60 keyword-only and 46/60 fused (MRR@10 0.782 / 0.662 / 0.826). Exact identifiers went from 2/12 to 9/12. Paraphrases went from 15/24 down to 13/24, because the weak lexical list gets an equal vote. Hit@5 did not move (55 → 55). Fusion fixes ranking more than recall, and it can hurt paraphrase queries. So fusion belongs in a **third peer tool** for the "unsure" case, with both arms still selectable as their own tools. It must not replace either of them or rank above them. Every 2026 headless peer (Vault Cortex, Basic Memory, OpenClaw's memory search) ships a fused arm. The search evaluation harness (#356) now exists, so the default can be measured on the operator's own judgments rather than taken on faith.

## What Changes

- **A new read tool, `hybrid_search(query, limit=10, folder?, tags?, frontmatter?)`**, the 28th tool, registered last with `title="Hybrid search"` and the shared `_READ_ONLY` annotations, wrapped by `_tracked` with the `MAX_SEARCH_QUERY_CHARS` cap on `query`, in concurrency class `embedding` (it makes the same provider round trip as `semantic_search`). `CLASS_MAPPING_VERSION` goes from 4 to 5.
- **A service function `hybrid_search` in `src/services/hybrid.py`** runs both arms in **one session, one `REPEATABLE READ, READ ONLY` transaction and one snapshot**, under the same `apply_note_filters` predicate. The keyword arm takes 50 rows with the existing `match: all` then `match: any` fill. The semantic arm takes a 50-chunk overfetch with per-note dedupe, plus the existing three `SET LOCAL`s, the full-precision re-sort and the zero-row exact fallback. The two lists are fused by **reciprocal rank fusion over note paths**: `score = Σ 1/(k + rank)`, with `k = HYBRID_RRF_K` (default **60**) and a fixed, arm-neutral tie-break. The query is embedded **before** the transaction opens, so no connection is held during the provider call.
- **The two existing services are refactored, not changed.** Each existing service is split into an arm core (statements only, with no `SET TRANSACTION`, no telemetry and no embedding call) and its unchanged wrapper. The projection-identity and keyword-ranking suites run unmodified, so `keyword_search` and `semantic_search` return what they return today.
- **An embedding failure degrades to the keyword arm, visibly and never silently.** If the provider raises, or rejects the input as too large, the tool returns the keyword arm alone in keyword order. The header says `arms: keyword-only (semantic unavailable: provider_error | provider_input_rejected)`, and so does the zero-result line. The usage row records `arms` and `semantic_unavailable`. A database error in either arm fails the whole call. There is no semantic-only mode.
- **Per-result provenance on one line.** Each result line carries the fused score, `semantic_rank` (with similarity) or `-`, `keyword_rank` (with `match` and `matched_in`) or `-`, a one-line `explain` holding the RRF terms that produced the score, the `stale` / `embedding_truncated` markers, and one preview. The preview is the arm that ranked the note better: a keyword `snippet:` highlight or `head:`, or the semantic `chunk:` (withheld when stale). Every note-controlled field (title, path, tags, preview) is a JSON string literal under the `get_changes` escaping rule, in a fixed-key object, and the server-authored fields follow it. A note can therefore forge neither a result row nor a provenance field. RRF is computed over each arm's top 50, and an always-present `arm_depth` header token says when an arm was full. The response is bounded by `MAX_READ_RESPONSE_CHARS`: rows are dropped whole from the end, and an abbreviated first row guarantees progress.
- **Symmetric docstrings across the three peers**: identifiers → `keyword_search`, paraphrase → `semantic_search`, unsure → `hybrid_search`. No tool is "primary". The server instructions' 512-character lead names all three. The lead stays ≤ 512 characters, the whole text ≤ 2,000, and every description ≤ 4,000.
- **One new setting, `HYBRID_RRF_K`** (int, 1–1000, default 60), documented in README and `.env.example`.
- **The harness can replay and A/B it.** `scripts/search_eval_arms/hybrid.py` exposes `make_arm` (membership `keyword_or_semantic`, a new harness membership: keyword OR semantic, with per-constituent corpus loss; `--arm-opt hybrid_k=…`, defaulting to the setting) and `make_arm_alt` (`--arm-opt hybrid_alt_k=…`, required), so one report can hold two values of k. The miner, the export SQL and the panel's search analytics treat `hybrid_search` rows like the other two search tools.
- **Docs in the same PR**: README (tool list, settings), `docs/architecture/search.md` (new "Hybrid search (#354)" section; the "no hybrid fusion (#354)" limitation struck), `docs/architecture/vault-tools.md` (tool-metadata table, size caps), `docs/architecture/rate-limits.md` (class table), `docs/architecture/usage-attribution.md` (new params keys), CLAUDE.md (MCP tools 27 → 28, the #343 read-only count, a key-decisions bullet).

No migration. No change to `keyword_search`'s or `semantic_search`'s arguments, ranking or output.

## Capabilities

### New Capabilities

- `hybrid-search`: the `hybrid_search` tool and service: arm composition, one-snapshot execution, RRF fusion and tie-break, degradation on embedding failure, rendering and provenance, response bound, telemetry, concurrency class and the `HYBRID_RRF_K` setting.

### Modified Capabilities

- `mcp-request-routing`: MODIFIED "Every registered tool SHALL publish a title and a complete set of behaviour annotations" (28 tools, `hybrid_search` among the read-only set), "The server SHALL publish bounded instructions whose lead states the contract" (the lead names the three search peers), and "Tool metadata SHALL leave the published tool surface otherwise unchanged" (the additions fixture gains `hybrid_search` as its third entry).
- `search-evaluation`: MODIFIED the mining and export requirements (`hybrid_search` rows are search rows) and the drift/corpus-loss requirement (the new `keyword_or_semantic` membership), and ADDED "The harness SHALL ship a replayable hybrid arm whose fusion constant is an arm option".
- `panel-search-analytics`: MODIFIED "Search result telemetry" and "Search analytics views" (`hybrid_search` records the same keys and gets its own query table).

`vault-guide` is not touched, because the primer names no search tool. `search-quality` is not modified: its requirements bind `semantic_search` and `keyword_search`, which do not change, and the `hybrid-search` spec states the same guarantees for its arms.
