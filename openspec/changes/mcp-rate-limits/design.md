## Context

- `/mcp` is mounted at `src/main.py:437` as `APIKeyMiddleware(mcp_handler)`, outside the slowapi limiter (`src/limiter.py`, keyed on remote address) that decorates every other public route.
- `APIKeyMiddleware` already loads the credential row and binds seven request-scoped ContextVars from it. The house rule is explicit: *the row is in hand, do not add a round trip.* An eighth costs nothing.
- `oauth_tokens.grant_id` is **NOT NULL** and indexed (migration 014, #64): every row minted from one `/authorize` approval shares it and every rotation inherits it. It is on the token row the middleware already selects.
- `_tracked` (`src/mcp_server/tools.py:626`) is the decorator all 25 tools inherit. It runs three pre-body gates in a fixed order — vault admission (#66), the unencodable-argument screen (#149), the daily quota (#162) — and maps each through `refusal_result` so a structured tool refuses in its declared shape.
- `FastMCP(stateless_http=True)`: every tool call is an independent POST, so there is no session-level serialisation to lean on.
- **One worker.** `Dockerfile:31` — `uvicorn … --workers 1`. Verified, and load-bearing throughout.
- Pool is 5 + 10 with `statement_timeout` 60 s; embedding calls have a 30 s bound; the indexer is one sequential pass under `index_pass_lock` shared by every tenant (#202).
- `delete_note` and `delete_file` default to `permanent=False` (trash), which is the only reason a write-rate bound is a recovery window rather than a last line of defence.
- Precedents for an argument cap: `MAX_LIST_PATTERN_CHARS` (1,024, #204) and `MAX_NOTE_BYTES`.

## Goals / Non-Goals

**Goals.** Bound what one principal — API key *or* OAuth grant — and what one *tenant* can do per unit time and at one instant, on a single worker, with no I/O added to the common path and no unbounded state; make every refusal machine-parseable by the agent that receives it; make the pressure visible where an operator already looks, without letting the refusals themselves become the load.

**Non-Goals.**
- **Indexer fairness (#202).** Round-robin over `_active_user_ids()`, a per-tenant chunk budget and a max-chunks-per-note cap belong to that issue. This change bounds the *rate at which work is created*; the two compose.
- **Expiring unused DCR clients.** `/register` grows `oauth_clients` unbounded (18 rows in production; `cleanup_expired_tokens` deletes only codes and tokens). OAuth housekeeping, not a rate control. **Recorded as a residual on #194**, which the archive step must note.
- Distributed or persisted limiter state, per-tenant billing, a Traefik `ratelimit` label, or changing the daily quota's UTC-day semantics.
- Per-IP limits on *authenticated* traffic. The principal is the right key; an IP is a bad proxy for it behind shared egress.

## The layers

Outermost to innermost. Each layer exists because the one inside it cannot see the load the outer one sheds.

| L | Control | Where | Scope key | Default (setting) | Refusal |
|---|---|---|---|---|---|
| 0 | In-flight admission ceiling | `APIKeyMiddleware`, **before any SQL** | process | 64 (`MCP_MAX_INFLIGHT_REQUESTS`) | HTTP **503** + `Retry-After`, no query, no usage row |
| 1 | Failed-auth budget | `APIKeyMiddleware`, before the credential lookup | client IP slot (salted hash table) | 60 / 300 s (`MCP_AUTH_FAILURE_LIMIT`, `MCP_AUTH_FAILURE_WINDOW_SECONDS`; null ⇒ off) | HTTP **429** + `Retry-After`, no query |
| 2 | General velocity bucket | `_tracked`, first gate | principal | 120/min, burst 30 (`MCP_RATE_LIMIT_PER_MINUTE`, `MCP_RATE_LIMIT_BURST`) | in-band, `code: rate_limited`, `scope: principal` |
| 3 | Write velocity bucket | `_tracked`, immediately after L2, write tools only | principal | 60/min, burst 15 (`MCP_WRITE_RATE_LIMIT_PER_MINUTE`, `MCP_WRITE_RATE_LIMIT_BURST`) | in-band, `code: rate_limited`, `scope: principal_write` |
| 4 | Vault admission (existing #66) | `_tracked` | user | — | in-band, `code: no_vault_assigned` |
| 5a | Unencodable-argument screen (existing #149) | `_tracked` | argument | — | in-band, `code: argument_not_encodable` |
| 5b | Argument length cap | `_tracked`, beside 5a | argument | 8,192 chars (`MAX_SEARCH_QUERY_CHARS`) | in-band, `code: argument_too_long` |
| 6 | Concurrency slots | `_tracked`, around the body | see below | see below | in-band, `code: slot_timeout` |
| 7 | Daily quota (existing #162) | `_tracked`, **after** slots | api key | `DEFAULT_DAILY_REQUEST_LIMIT` 5,000 for new keys | in-band, `code: over_quota` |

Slot levels at L6, acquired in this order and released in reverse:

| Order | Slot | Scope key | Default |
|---|---|---|---|
| 1 | per-principal-per-class | `(principal, class)` | embedding 1 (`MCP_MAX_CONCURRENT_EMBEDDING_PER_PRINCIPAL`) |
| 2 | per-principal, all classes | principal | 4 (`MCP_MAX_CONCURRENT_PER_PRINCIPAL`) |
| 3 | per-tenant-per-class | `(user_id, class)` | embedding 1 (`MCP_MAX_CONCURRENT_EMBEDDING_PER_USER`) |
| 4 | per-class | class | embedding 2, vector 4, write 4 |
| 5 | global | process | 12 (`MCP_MAX_CONCURRENT_TOOL_CALLS`) |

Classes: `embedding` = `semantic_search`; `vector` = `find_related`; `write` = `create_note`, `edit_note`, `move_note`, `delete_note`, `set_frontmatter`, `write_file`, `delete_file`, `import_from_url`. Every other tool takes only levels 2 and 5. `request_upload` / `request_download` / `check_upload` only mint or read capability rows; the bytes travel over `/transfer/*`, which has its own semaphore and is not a tool call.

## Decisions

**D1. Layer 0 exists because a limiter that starts after authentication is not a limiter.** Every per-principal control below needs a principal, and getting one costs an `async_session()` checkout plus an indexed SELECT. Ten thousand concurrent calls from a *valid* credential therefore exhaust the 5 + 10 pool on the lookups alone, and every other tenant gets a 500 after `pool_timeout`, before L2 ever sees a request. So `APIKeyMiddleware` increments a plain integer at entry, decrements it in `finally`, and answers 503 + `Retry-After` when it is at `MCP_MAX_INFLIGHT_REQUESTS` — no session, no query, no usage row (there is no authenticated call to attribute one to). 503 rather than 429 because this is server capacity, not the caller's allowance. The ceiling must exceed the global slot ceiling, since a request waiting for a slot holds an in-flight count; validated at boot. `stateless_http=True` keeps every request short, so the counter tracks real concurrency rather than idle streams.

**D2. Refusal recording is bounded, and it is bounded by coalescing rather than by silence.** A refusal is cheap to produce and, before this, wrote one `usage_logs` INSERT each — so the cheapest thing an agent could do was generate database writes. L2 already bounds that to 120/min/principal, but the honest fix is to stop the *log* being the amplifier: rate and slot refusals are coalesced per `(principal, tool, marker)` per `MCP_REFUSAL_LOG_INTERVAL_SECONDS` (10 s), and the representative row carries `suppressed: <n>` counting the ones it stands for. The alternative Codex offered — the gate refusal writes no row — is **rejected**: an operator opening `/admin/performance` to find out why an agent is stalled must see the pressure, and a limiter that is invisible in the log is one nobody can diagnose or size. `suppressed` is a JSON **integer** and the performance view's refusal count sums `1 + suppressed`, with a guarded cast (`~ '^[0-9]+$'`), following the `result_count` precedent rather than the unguarded `over_quota` one.

**D3. The principal is the grant, not the token, and not (client, user).** `oauth_tokens.grant_id` is NOT NULL, indexed, shared by every rotation of one `/authorize` approval, and already on the row the middleware loads — so `("oauth", grant_id)` costs no query. Keying on `oauth_tokens.id` would hand a refreshing agent a fresh allowance every hour. Keying on `(client_id, user_id)` — the first draft — merges two grants that #64 made independently revocable, so revoking one would not free the other's allowance and an operator's stop would look like it had not worked. `("api_key", api_keys.id)` for the other branch. `current_principal` is set and `reset()` in the same `finally` as the other ContextVars.

**D4. No principal ⇒ no per-principal control, deliberately.** Sandbox mode short-circuits the middleware; a direct in-process caller never passes it. Both read `None` and are exempt, the same shape as `_quota_admission_error`'s "a limit with no key is exempt rather than a crash". Fail-open is correct here because nothing untrusted reaches that path — untrusted traffic arrives through the middleware, which binds a principal or returns 401/429/503. Layers 0 and 1 are *not* keyed on the principal and apply regardless.

**D5. Gate order, and the two rules that fix it.** L2 → L3 → L4 → L5 → **L6 (slots)** → **L7 (quota)** → body.
- *A token is not a slot.* A rate token refills, so consuming one on a call that a later gate refuses is correct — the refusal itself costs work. That is why the buckets come first, and why the flood we most want to shed cheaply (calls that were going to be refused anyway) is shed by pure arithmetic.
- *Nothing durable is consumed by a call that does not run.* This is #162's invariant and the first draft broke it: a key that passed quota admission and then timed out waiting for a slot had spent a daily slot on a call that never executed, unrecoverably. So slots are acquired **before** quota admission and are released in the `finally` that covers the quota gate as well as the body. #162's own reasoning — "the quota is the last pre-body gate so a call refused for having no vault consumes nothing" — is preserved exactly; the slot wait simply joins the set of things that must resolve before the counter moves. Slots are momentary and self-releasing; the counter is not.

**D6. Slot acquisition order is fixed, and the order is the design.** Narrowest scope first, released in reverse in a `finally`. A fixed total order makes deadlock impossible (a task holds at most five, always in this order). The *choice* follows one rule — while you wait, hold only resources whose contention hurts the fewest others: a principal-scoped hold blocks one principal, a tenant-scoped hold blocks one tenant, so those are taken before the shared ones. The residual is that a task holds a class slot while waiting for the global one; that is why boot validation **requires** `MCP_MAX_CONCURRENT_TOOL_CALLS ≥ embedding + vector + write` (12 ≥ 10 at the defaults), so the global ceiling can never be the thing a classed call queues behind. Codex was right that the first draft asserted this relationship in prose and did not enforce it; asserting it and not enforcing it is how the reasoning quietly stops being true.

**D7. The per-tenant embedding cap is the cross-tenant guarantee; a per-tenant *reservation* is not on offer.** One user holding both an API key and an OAuth grant is two principals, so per-principal caps alone let that user occupy the whole two-slot embedding class and starve the other tenant — exactly the failure this change exists to prevent, reintroduced one level up. `MCP_MAX_CONCURRENT_EMBEDDING_PER_USER` (1) closes it: tenant A holds at most one slot however many credentials it presents, so tenant B always has one. A true *reservation* per tenant is **rejected** as unimplementable at this size: with two slots and N tenants there is nothing to reserve, and a reservation scheme that cannot guarantee anything is worse than a cap that can. Single-user and ownerless traffic (`user_id IS NULL`) is one tenant, consistent with the owner predicate being total (#127).

**D8. Two buckets, because velocity and destruction are different questions.** The general bucket is a **velocity** bound: it stops a hot loop and bounds the rate at which any work is created. It is *not* a blast-radius bound, and describing it as one was wrong — 120 deletes/minute empties a 2,577-note vault in about twenty minutes. The write bucket (60/min, burst 15, on the eight mutating tools, taken in addition to the general one) halves that, and the actual totality bound is the daily quota: 5,000 admissions ceiling the day regardless of how they are spent. Two further facts are load-bearing and belong in the same sentence as the numbers, so nobody mistakes this for a solved problem: `delete_note` / `delete_file` default to `permanent=False`, so the common case is recoverable from trash; and rate limiting *never* prevents a single destructive write, which is what the `vault-tools` disciplines are for. **The 60/15 numbers are an owner decision, recorded in Open Questions.**

**D9. One caller-visible refusal shape, composed with every tool output type.** `params.error` is invisible to the caller — it is an operator's field — so the first draft's "typed, actionable refusal" was prose in a string for `keyword_search` and every other `str`-returning tool. A new `src/services/refusals.py` (importing nothing from the app, so `tools.py`, `quotas.py` and `rate_limits.py` can all use it without a cycle) defines a `Refusal` carrying `code`, `scope`, `limit`, `limit_unit` and `retry_after_seconds`, and one renderer that appends a final line to the existing human prose:

```
MCP-REFUSAL {"code":"slot_timeout","scope":"slot:embedding","limit":2,"limit_unit":"concurrent_calls","retry_after_seconds":5}
```

- `str`-returning tools receive prose + that line. Structured tools receive the identical complete text in their declared error field through the existing `refusal_result` mapping (`ReadNoteResult(error=…)`), so no output-schema validation can fail and both kinds of tool carry the same fields.
- The sentinel is a fixed line-initial token so an agent can locate it without parsing prose, and the JSON is one line so it survives being quoted into a transcript.
- `retry_after_seconds` is always a JSON number ≥ 1 where retrying can help — the whole seconds until one token is available (L2/L3), the wait budget (L6), the seconds to the next UTC midnight (L7). It is **absent** for `no_vault_assigned` and `argument_not_encodable`, where retrying is futile and a number would invite a loop.
- The three existing pre-body refusals adopt the line **additively**: their prose is unchanged, so every `in` / `startswith` assertion and every agent reading them still works, and the family becomes uniform in one step rather than leaving two conventions.

**D10. Nothing blocks while holding the loop, and nothing adds I/O.** A bucket update is a synchronous function — read `(tokens, last_refill)`, compute, write back — with no `await` between read and write, so on a single-threaded event loop it is atomic by construction and needs no lock. `asyncio.Semaphore` construction does not bind a loop in Python 3.12, so class and global semaphores are module-level; principal- and tenant-scoped state is lazy. The admitted common path is a few dict lookups, some floats, and semaphore acquisitions that succeed immediately: no statement, no session checkout. Pinned by a statement-counting test, as `tests/test_issue_162_quota_gate.py` pins the quota gate — that is the only way this regresses invisibly.

**D11. One deadline across all five acquisitions, not five timeouts.** `deadline = monotonic() + MCP_SLOT_WAIT_SECONDS`; each `asyncio.wait_for` gets the remaining budget. Five independent timeouts would make the worst case 25 s, a latency regression sold as a limiter. The elapsed wait is *approximately* the budget, not exactly it: the deadline is checked between acquisitions and the loop may schedule late, so the spec says approximately and the test asserts a small tolerance rather than an exact bound.

**D12. Limiter state is bounded by construction, and each registry says how.**
- **Principals and tenants**: a dict with a hard cap (`MCP_LIMITER_MAX_TRACKED_PRINCIPALS`, 10,000) and TTL eviction, swept amortised on insert (a bounded number of expired entries per admission — never a background task this server does not otherwise need). An entry is evictable only when it is **full and idle**: evicting a *depleted* bucket would grant free capacity, and evicting one with in-flight holders or waiters would corrupt the count, so the sweep skips both. On overflow the extra principals share **one overflow bucket** rather than failing open or closed — cardinality here is bounded by the number of credentials that exist, which requires authentication to grow, so overflow means something has gone very wrong and the safe answer is "still limited, just less precisely" rather than "unlimited" (fail-open lets the attack succeed) or "refused" (fail-closed turns a bookkeeping cap into an outage for a legitimate credential).
- **Addresses** are different: cardinality is unbounded and *unauthenticated*, so eviction is a losing game. The failed-auth budget uses a **fixed-size table** of `MCP_AUTH_FAILURE_TABLE_SIZE` (4,096) counters indexed by a **per-process-salted** hash of the address. Memory is O(size) by construction, there is nothing to evict, and the only cost is that two addresses may share a slot — which makes the control stricter, never weaker. The salt is per-process and random so nobody can choose to collide with a victim.
- High-cardinality tests are part of the contract: 100,000 distinct principals and 100,000 distinct addresses must leave memory bounded and must not refuse a legitimate credential.

**D13. Limiter state is in-process and not persisted.** A restart begins with every bucket full and every slot free. Sound because: there is exactly **one** uvicorn worker, so there is one copy of the state; instantaneous pressure is meaningless to persist across a process that no longer exists; a restart is an operator action or a crash, not something a caller can induce; and the *durable* ceiling already exists in PostgreSQL as `quota_counters`, of which these are the burst layer. **The worker count is part of the contract** — `--workers N` silently multiplies every in-process limit by N. A comment goes at the `CMD` and the architecture note says it in prose.

**D14. Boot validation, and one representation for "off".** A `model_validator` enforces: `global ≥ embedding + vector + write` (D6); `per_principal ≤ global`; `embedding_per_principal ≤ embedding_per_user ≤ embedding class`; `max_inflight ≥ global`; a bucket's rate and burst are both set or both null; and **zero is rejected everywhere**, for #162's reason (a control that refuses every call reads as an outage, not a setting). Null is the only disable, following `daily_request_limit`'s NULL-is-unlimited idiom rather than inventing a second convention — and because `.env` has no JSON null, one central `BeforeValidator` maps an empty value, `null` or `none` (stripped, case-insensitive) to `None` for every nullable limiter setting. That is implemented in `Settings` and tested **through a real env file**, because a validator that only works when the value arrives as a Python `None` is not the thing the operator will exercise.

**D15. The query cap is a declarative screen in `_tracked`, not a check inside each search body.** In a body it would be a *post*-body marker under the classification rule in `docs/architecture/usage-attribution.md` — a ~0 ms row inside the latency percentiles, mis-measuring in the direction nobody can see from the page. `_tracked` already carries a generic per-argument screen (`_first_unencodable_argument`), so `arg_char_caps={"query": MAX_SEARCH_QUERY_CHARS}` sits beside it and generalises. The refusal precedes the provider call, the `tsquery` parse and any search statement; it does **not** precede the usage row, which is still written (subject to D2 coalescing) — the first draft's "no database statement" was too broad and would have made the refusal invisible.

Note what the cap is *not* for: #194's verification withdrew the cost-amplification claim (Ollama truncates to the model context, OpenAI rejects over 8,192 tokens). The reasons are: an unbounded argument interpolated into `f"No results for '{query}'"`, which is exactly the discipline #149 imposed everywhere else; `tsquery` parsing on the single event loop, the same class as #204; and an OpenAI-provider deployment currently turning an over-long query into a *provider error* where the contract promises a typed in-band refusal.

**D16. The failed-auth budget lives in the app, and Traefik is the wrong instrument.** A reverse proxy cannot condition on the response status, so a `ratelimit` label on `obsidian-mcp-api-rtr` would throttle authenticated agents to bound unauthenticated probing — and `/transfer/*`, `/health` and `/.well-known` share that router. The host's Traefik static configuration is also outside this repo (`CLAUDE.md`, "Public repo — host paths live outside the tree"), so a control expressed there would not be reproducible from the tree. Decision: in `APIKeyMiddleware`; `docker-compose.yml` labels unchanged, with a comment recording that this was decided rather than missed.

Three details make it correct. The address comes from `ProxyHeadersMiddleware`, which is added on the app and therefore wraps the mount — a budget keyed on a spoofable header is worse than none, and `request-trust`'s restricted-proxy-header requirement is the dependency. **Every** 401 branch increments — missing Bearer, invalid key, ownerless credential, inactive user, expired credential, cross-user grant, missing vault scope — because a prober can pick whichever branch is cheapest, and a budget that covers six of seven bounds nothing. A request with **no** client address (`scope["client"] is None`) is charged to one reserved slot shared by all address-less requests, rather than exempted: exempting is a bypass anyone who can strip the header gets for free.

**D17. Threshold and `Retry-After` arithmetic, stated so they cannot drift.** The budget refuses when the count *already recorded* in the current window is `≥ MCP_AUTH_FAILURE_LIMIT` — so with a limit of 60 the 61st failure in the window is the first refused, and a refused request does not increment (it never reached authentication). `Retry-After` is the whole number of seconds remaining in the current window, minimum 1. The same arithmetic in one helper, one test parameterised over every 401 branch.

**D18. 429, not a silent 401.** An over-budget response is distinguishable, which tells a prober the limiter exists. Fair trade: the limiter is documented, a legitimate client with an expired token deserves an answer it can act on, and `Retry-After` is the only thing that turns a broken client's hot loop into a slow one.

**D19. The default daily limit is applied in application code, never as a column default.** A `server_default` would be a schema change, would apply to every future insert path, and still could not express "grandfather the rows that exist". The JSON API distinguishes omitted from explicit-null by `"daily_request_limit" in req.model_fields_set` — `null` is documented as *unlimited* and must stay so. The **panel is different**: the default is materialised only as the create form's pre-filled value, and a blank submitted field is an explicit "unlimited" with **no POST-side substitution**, so what the operator saw is what they get and there is exactly one place the default can be overridden. `keys_page` passes the configured default to the template.

**Why 5,000.** Production is ~1,600 tool calls per 30 days across all credentials, so 5,000/day is roughly two orders of magnitude of headroom and cannot plausibly interrupt a real session, while a runaway stops the same day. At 120/min it takes at least ~42 minutes to spend, so the controls are consistent rather than one making the other unreachable. It binds only keys created *after* this ships.

**D20. Three markers, not one.** `rate_limited` (either bucket, distinguished by `scope`), `slot_timeout` (a slot wait) and `argument_too_long` (the cap). The first draft folded the bucket and the slot into one marker distinguished only by a `rate_limit_scope` string; splitting them means the two questions an operator actually asks — "is one agent too fast?" versus "is the server at capacity?" — are answerable by the marker alone, without parsing a scope. All three are **pre-body** by the classification rule and all three join `pre_body_refusal_sql()`. `rate_limit_scope` remains a string no reader casts, outside the reserved numeric/boolean key hazard; `suppressed` is an integer and is read with a guarded cast.

## Rejected findings

Recorded with reasons, per the review protocol.

- **"…or the gate refusal writes no row" (BLOCKER 1, second half).** Rejected in favour of coalescing (D2). A limiter that leaves no trace is one an operator cannot diagnose or size, and `/admin/performance` is where they would look. Coalescing bounds the INSERT rate to one row per `(principal, tool, marker)` per 10 s while `suppressed` keeps the totals exact.
- **A per-tenant *reservation* for the embedding class (MAJOR 2, second half).** Rejected as unimplementable at this size; the per-tenant **cap** is folded in instead (D7). With two slots and an unbounded number of tenants there is nothing to reserve, and a reservation that cannot guarantee a slot is a promise the design would break under exactly the load it exists for.
- **"The generic bucket does not bound destructive blast radius" — accepted as a correction, not as a solution (MAJOR 3).** The write bucket is folded in per the owner decision, but the proposal now says plainly that *no* rate bucket bounds totality: 60 deletes/minute still empties this vault in under an hour. The totality bound is the daily quota, the recovery path is `permanent=False`, and neither is a substitute for the `vault-tools` write disciplines. Recorded so the number is not mistaken for a guarantee.

## Alternatives rejected

- **slowapi on the `/mcp` mount.** Keyed on the remote address (wrong scope: shared egress merges tenants, one tenant with two agents is one bucket) and decorator-shaped for routes, not an ASGI mount; it produces an HTTP 429 where the contract needs a parseable in-band tool result.
- **A Traefik `ratelimit` middleware as the primary control.** D16.
- **Making the daily quota the burst control by lowering it.** A per-day counter cannot bound concurrency at all, and a low daily number to approximate a rate would exhaust a legitimate agent's day in one healthy burst. #188's own recommendation is necessary and insufficient.
- **Persisting bucket state in PostgreSQL** (the `quota_counters` shape). A statement on the hottest path in the server to bound something meaningless once the process is gone, with the durable ceiling already one layer up. D13.
- **An unbounded queue instead of a bounded wait.** Queuing turns a rate problem into a latency problem: the caller's connection is held, the pool behind it, and the agent gets no signal to back off. Every wait has a deadline and every deadline resolves to a refusal carrying `retry_after_seconds`.
- **Per-tool-name semaphores.** More knobs, no more protection: the scarce resources are the embedding provider, HNSW/pool time and the indexer. Three classes name exactly those.
- **Refunding a slot on a failed body, or a token on a refusal.** #162's reasoning in both directions: a tool that always fails would be free.
- **Enforcing the query cap inside the search bodies.** D15 — a post-body marker polluting the percentiles.
- **Fail-open or fail-closed on principal-registry overflow.** D12 — a shared overflow bucket is bounded *and* keeps a legitimate credential working.

## Risks / Trade-offs

- **Layer 0 is a global ceiling, so a flood does degrade everyone — into a fast 503 rather than a pool timeout.** That is the trade being made: 64 in-flight is above any legitimate concurrent load here, and a caller that gets `Retry-After` immediately is strictly better off than one that gets a 500 after `pool_timeout`. It is nonetheless the one control that can refuse a well-behaved tenant because of another's traffic, which is why it sits above a generous default and why the per-principal layers below it exist to make reaching it unlikely.
- **Shared egress IPs and the failed-auth budget.** claude.ai's MCP client egresses from shared addresses, so one tenant's broken client can spend another's failure budget; the hashed table can also merge two addresses into one slot. Mitigated by a generous default (60 failures / 5 min — no working client fails 60 times in 5 minutes), by `MCP_AUTH_FAILURE_LIMIT` = null as an escape hatch, and by one WARNING naming the address the first time a slot engages. **Declared, not closed.**
- **Two different principals can still make a third wait.** With the per-tenant embedding cap at 1, two tenants can occupy the class and a third waits out the budget and is refused. Honest outcome for a resource the provider serialises anyway, not a defect.
- **A shared key is a shared bucket.** Two agents on one credential contend, exactly as they do for the daily quota. Same answer as #162: an agent that deserves isolation deserves its own credential.
- **Coalescing means the log is a summary, not a transcript.** The row count is no longer the refusal count; `1 + suppressed` is. Every reader of those markers must be updated together, which is why the predicate, the aggregate and the test move in one slice.
- **The defaults are guesses against a small sample** (~1,600 calls/30 days). Every one is a setting, refusals are counted per tool on `/admin/performance`, and the first week after deploy should be read there before any number is treated as settled.
- **New gates on the hottest path.** Mitigated by D10 and pinned by statement-counting and latency tests.
- **`--workers 1` becomes load-bearing.** D13, recorded in the Dockerfile, the architecture note and the spec.
- **The new-key default can surprise an operator.** The refusal names the limit and points at the panel (#162), the keys page shows consumption, and the create form states the default.

## Migration Plan

None. No schema change, no backfill, no new dependency. `make db-check` still runs after deploy. Rollback is a redeploy of the previous image — settings are read at boot and nothing is persisted. Every control can be disabled in `.env` without a code change: null the nullable settings, raise the concurrency numbers, null `DEFAULT_DAILY_REQUEST_LIMIT`.

## Open Questions

Every default is a setting; these are the ones that want the owner's word. None blocks implementation.

1. **General bucket — 120/min, burst 30?** Recommended: far above observed usage, stops a hot loop within a second, burst covers a post-search fan-out.
2. **Write bucket — 60/min, burst 15?** Owner decision recorded; the number to weigh is that 60/min still reaches every note in this vault in about three quarters of an hour, so it is a *velocity* bound and the daily quota is what bounds totality (D8). 20/min would make bulk destruction obvious long before it completed, at the cost of slowing a legitimate bulk import through `write_file`.
3. **`DEFAULT_DAILY_REQUEST_LIMIT` — 5,000?** Recommended (D19). Alternative worth considering: 2,000, still ~40× observed usage, halving a runaway's reach.
4. **`MCP_MAX_INFLIGHT_REQUESTS` — 64 against a 5 + 10 pool?** Recommended: high enough that legitimate concurrency never reaches it, low enough that the queue behind it cannot outlive the slot wait.
5. **`MCP_AUTH_FAILURE_LIMIT` — 60 per 5 minutes?** Recommended, with the shared-egress risk as the reason it is not lower.
6. **`MCP_MAX_CONCURRENT_TOOL_CALLS` — 12 against a 5 + 10 pool?** Recommended: below the pool so a saturated tool surface still leaves connections for the panel, the indexer and `/health`, and ≥ the sum of the class caps as D6 requires.
7. **Should existing production keys be given a limit at deploy time?** #194 recommends it. This change deliberately does not touch them (grandfathering is D19's whole point); setting 5,000 on the five live keys is a one-minute panel action and belongs in the post-deploy checklist.
