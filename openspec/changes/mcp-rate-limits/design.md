## Context

- `/mcp` is mounted at `src/main.py:437` as `APIKeyMiddleware(mcp_handler)`. It is outside the slowapi limiter (`src/limiter.py`, keyed on remote address, wired at `src/main.py:298`), which decorates only `src/api/routes.py`, `src/auth/routes.py`, `src/oauth/routes.py` and `src/transfer/routes.py`.
- `APIKeyMiddleware` already loads the credential row and binds five request-scoped ContextVars from it (`current_permission`, `current_api_key_id`, `current_oauth_token_id`, `current_user_id`, `current_vault_root`, `current_actor`, `current_daily_request_limit`). The house rule is explicit: *the row is in hand, do not add a round trip.* A sixth ContextVar costs nothing.
- `_tracked` (`src/mcp_server/tools.py:626`) is the shared decorator all 25 tools inherit. It already runs three pre-body gates in a fixed order — vault admission (#66), the unencodable-argument screen (#149), the daily quota (#162) — and maps every one of them through `refusal_result` so a structured tool refuses in its own shape.
- `FastMCP(stateless_http=True)` (`src/mcp_server/server.py:93`): every tool call is an independent POST, so there is no session-level serialisation to lean on.
- **One worker.** `Dockerfile:31` — `uvicorn … --workers 1`. Verified, and load-bearing for everything below.
- Pool is 5 + 10 with `statement_timeout` 60 s (`src/database.py`); embedding calls have a 30 s per-call bound; the indexer is a single sequential pass under `index_pass_lock` shared by every tenant (#202), so a write tool's cost does not end when the tool returns.
- Two constants precedents for an argument cap: `MAX_LIST_PATTERN_CHARS` (1,024, #204) and `MAX_NOTE_BYTES`.

## Goals / Non-Goals

**Goals.** Bound what one principal — API key *or* OAuth grant — can do per unit time and at one instant, on a single worker, without adding I/O to the common path; make every refusal something an agent can act on; make the pressure visible where an operator already looks.

**Non-Goals.**
- **Indexer fairness (#202).** Round-robin over `_active_user_ids()`, a per-tenant chunk budget, and a max-chunks-per-note cap belong to that issue and that change. This one bounds the *rate at which work is created*, which is a different lever; the two compose.
- **Expiring unused DCR clients.** `/register` grows `oauth_clients` unbounded (18 rows in production; `cleanup_expired_tokens` deletes only codes and tokens). It is OAuth housekeeping, not a rate control, and it belongs with the token-cleanup job. **Recorded as a residual on #194** — not closed by this change, and #194's issue text should say so at archive time.
- Distributed or persisted limiter state, per-tenant billing, a Traefik `ratelimit` label, or changing the daily quota's UTC-day semantics.
- Per-IP limits on *authenticated* traffic. The principal is the right key; an IP is a proxy for it and a bad one behind shared egress.

## Decisions

**D1. The principal is the grant, not the token.** OAuth access tokens live one hour and refresh; keying a bucket on `oauth_tokens.id` would hand a refreshing agent a fresh allowance every hour and make the control ornamental. `("oauth", client_id, user_id)` is stable across refresh, is already in hand at admission (the middleware's single token query `outerjoin`s `oauth_clients` and returns `client_name`; `client_id` is on the token row), and adds no query. Both components are needed: `client_id` alone would merge two users of one public client, and `user_id` alone would merge a user's separate clients. `current_principal` is set and `reset()` in the same `finally` as the other seven ContextVars, so it can never leak into another request.

**D2. No principal ⇒ no limit, deliberately.** In sandbox mode `APIKeyMiddleware` short-circuits and nothing is bound; a direct in-process caller (tests, the panel, a future internal job) never passes the middleware. Both read `None` and are exempt, which is the same shape as `_quota_admission_error`'s "a limit with no key is exempt rather than a crash". Fail-open here is correct because there is no untrusted caller on that path — everything untrusted arrives through the middleware, which always binds a principal or returns 401.

**D3. The bucket is the *first* gate; the quota stays the *last*.** New order in `_tracked`: **token bucket → vault admission → unencodable-argument screen → daily quota → [acquire slots] → body → [release slots]**.
- The bucket goes first because it is the only gate that is pure arithmetic, and a flood we want to shed cheaply is exactly a flood of calls that would be refused anyway. A rate token *is* consumed by a call that is then refused for having no vault — correctly: the refusal itself costs a log write, and a token refills, unlike a quota slot.
- The daily quota keeps its position as the last consuming gate, so #162's guarantee ("a call refused for having no vault or an unencodable argument consumes nothing") is untouched, and a *rate*-refused call now also consumes no quota.
- Slots are acquired **after** every admission gate, because a slot held by a call that was going to be refused is a slot stolen from one that would run.

**D4. Slot acquisition order is fixed, and the order is the design.** Narrowest scope first: per-principal-class → per-principal → class → global, released in reverse in a `finally`. A fixed total order means no deadlock (a task holds at most four, always in this order). The *choice* of order follows one rule — while you wait, hold only resources whose contention hurts the fewest others: a principal-scoped hold blocks only that principal, so it is taken first. The remaining exposure is that a task holds a class slot while waiting for the global one; that is why the global ceiling (12) is set above the sum of the class limits (2 + 4 + 4 = 10), so global contention comes from unclassed tools rather than from classed ones queueing behind each other. That relationship is checked at boot (D8), not left as folklore.

**D5. One deadline across all four acquisitions, not four timeouts.** `deadline = monotonic() + MCP_SLOT_WAIT_SECONDS`; each `asyncio.wait_for` gets the remaining budget. Four independent 5 s timeouts would make the worst-case wait 20 s, which is a latency regression sold as a limiter. A wait that ends without a slot is the same typed refusal as the bucket, with `retry_after_seconds` = the wait budget: the server is at capacity, and an agent that is told so can back off instead of holding a connection.

**D6. Nothing blocks while holding the event loop, and nothing adds I/O.** The bucket update is a synchronous function — read `(tokens, last_refill)`, compute, write back — with no `await` between read and write, so on a single-threaded event loop it is atomic by construction and needs no lock. `asyncio.Semaphore` construction does not bind a loop in Python 3.12, so the class and global semaphores can be module-level; per-principal state is created lazily. The admitted common path is: one dict lookup, a few floats, and (only for a classed tool) semaphore acquisitions that succeed immediately. No statement, no session checkout — the same property `tests/test_issue_162_quota_gate.py` pins for the quota gate by counting statements, and it should be pinned the same way here.

**D7. Limiter state is in-process and is not persisted — and that is the whole reason it is honest.** A restart clears every bucket (full) and every semaphore (free). Acceptable because: (a) there is exactly **one** uvicorn worker, so there is exactly one copy of the state and no cross-worker divergence — this is not "eventually consistent", it is *the* state; (b) the thing being bounded is instantaneous pressure, which has no meaning to persist across a process that no longer exists; (c) a restart is an operator action or a crash, not something a caller can induce, so it is not a bypass; and (d) the *durable* ceiling already exists and lives in PostgreSQL — `quota_counters` — and controls 1–3 are explicitly the burst layer beneath it. **The worker count is part of the contract:** `--workers N` silently multiplies every in-process limit by N. A comment goes next to the `--workers 1` in `Dockerfile` naming this change, and the architecture note says it in prose.

**D8. Configuration coherence is refused at boot, not discovered in production.** A `model_validator` requires `MCP_MAX_CONCURRENT_PER_PRINCIPAL ≤ MCP_MAX_CONCURRENT_TOOL_CALLS`, `MCP_MAX_CONCURRENT_EMBEDDING_PER_PRINCIPAL ≤ MCP_MAX_CONCURRENT_EMBEDDING_CALLS`, `MCP_RATE_LIMIT_BURST ≥ 1`, and `MCP_MAX_CONCURRENT_TOOL_CALLS ≥ max(class limits)`. An incoherent set is a ceiling that can never be reached or a per-principal cap larger than the pool it draws from — a setting that reads as enforcement and is not one. Null on either of the two nullable settings means *off*, following `daily_request_limit`'s established NULL-is-unlimited idiom rather than inventing a second disable convention; **zero is refused**, for #162's reason (a control that refuses everything reads to an operator as an outage, not a setting).

**D9. The query cap is a declarative screen in `_tracked`, not a check inside each search body.** Putting it in the body would make it a *post*-body marker under the classification rule in `docs/architecture/usage-attribution.md` — a ~0 ms row inside the latency percentiles, mis-measuring in the direction nobody can see from the page. `_tracked` already carries a generic per-argument screen (`_first_unencodable_argument`), so `arg_char_caps={"query": MAX_SEARCH_QUERY_CHARS}` sits directly beside it, runs before the provider call, before `tsquery` parsing, and before the query is interpolated into `f"No results for '{query}'"` — an unbounded interpolation into a server-authored message, which is exactly the discipline #149 imposed everywhere else. The cap is a module constant rather than a setting, matching `MAX_LIST_PATTERN_CHARS`.

Note what the cap is *not* for: the issue's own verification withdrew the cost-amplification claim (Ollama truncates to the model context, OpenAI rejects over 8,192 tokens). The real reasons are the three above plus one honest one — an OpenAI-provider deployment currently turns an over-long query into a *provider error*, where the contract promises a typed in-band refusal.

**D10. The failed-auth budget lives in the app, and Traefik is the wrong instrument.** A reverse proxy cannot condition on the response status, so a `ratelimit` label on `obsidian-mcp-api-rtr` would throttle authenticated agents to bound unauthenticated probing — and `/transfer/*`, `/health` and `/.well-known` share that router. The host's Traefik static configuration is also outside this repo, so a control expressed there would not be reproducible from the tree (see `CLAUDE.md`, "Public repo — host paths live outside the tree"). Decision: in `APIKeyMiddleware`; `docker-compose.yml` labels unchanged, with a comment recording that this was decided rather than missed.

Two details make it safe. The client IP must come from `ProxyHeadersMiddleware`, which is added on the app and therefore wraps the `/mcp` mount — a budget keyed on a spoofable header is worse than none, and `request-trust`'s restricted-proxy-header requirement is the dependency. And the check is a dict lookup *before* the credential lookup, so an over-budget IP costs no session checkout and no query — which is the actual harm being bounded, not credential guessing (256-bit `secrets.token_hex` keys make that unrealistic, as #194's verification says).

**D11. 429, not a silent 401.** An over-budget response is distinguishable, which tells a prober the limiter exists. That is a fair trade: the limiter is documented, a legitimate client with an expired token deserves an answer it can act on, and `Retry-After` is the only thing that turns a broken client's hot loop into a slow one.

**D12. The default daily limit is applied in application code, never as a column default.** A `server_default` would be a schema change *and* would apply to every future insert path, and it still could not express "grandfather the rows that exist". Both creation paths (`src/api/routes.py:125`, `src/control_panel/routes.py:661`) apply `settings.default_daily_request_limit` when the caller did not choose. For the JSON API, "omitted" and "explicitly null" must stay different — `null` is documented as *unlimited* — so the distinction is `"daily_request_limit" in req.model_fields_set`, not a truthiness test. The panel form pre-fills the default value and its help text says clearing it means unlimited.

**Why 5,000.** Production is ~1,600 tool calls per 30 days across all credentials, so 5,000/day is roughly two orders of magnitude of headroom for any real agent session and cannot plausibly interrupt one; it is small enough that a runaway loop stops the same day rather than running until someone notices. At the rate ceiling (120/min) it also takes a minimum of ~42 minutes to spend, so the two controls are consistent rather than one making the other unreachable. It binds only keys created *after* this ships.

**D13. Marker naming is coordinated.** `rate_limited` and `argument_too_long` are new values, distinct from the `permission_denied` / `tool_exception` pair that the parallel `security-event-logging` change adds, and from every existing marker. Both are **pre-body** by the classification rule in `docs/architecture/usage-attribution.md` (the body has not run), so both join the enumerated set in `pre_body_refusal_sql()` — otherwise a tool refusing thousands of calls an hour comes out looking fast on `/admin/performance`, which is precisely the failure that rule exists to prevent. `rate_limit_scope` is a **string** key: it is never cast by any reader, so it does not join the reserved-key hazard that `embed_ms` / `db_ms` / `over_quota` carry.

## Alternatives rejected

- **slowapi on the `/mcp` mount.** Its key function is the remote address, and its decorator model targets routes, not an ASGI mount wrapping a session manager. Keying on the IP is the wrong scope (shared egress merges tenants; one tenant with two agents is one bucket), and it produces an HTTP 429 where the contract requires a typed in-band tool result an agent can read.
- **A Traefik `ratelimit` middleware as the primary control.** See D10: cannot see the status code, cannot see the principal, and lands on a router shared with `/transfer` and `/health`.
- **Making the daily quota the burst control by lowering it.** A per-day counter cannot bound concurrency at all; a low daily number to approximate a rate would exhaust a legitimate agent's day in a single healthy burst. #188's own recommendation ("make a modest default daily quota opt-out rather than opt-in") is necessary and insufficient — hence controls 1 and 2.
- **Persisting bucket state in PostgreSQL** (the shape `quota_counters` uses). It would add a statement to every call on the hottest path in the server to bound something that is meaningless once the process is gone, and the durable ceiling already exists one layer up. Rejected on D7 and on "no I/O on the common path".
- **An unbounded queue instead of a bounded wait.** Queuing is how a rate problem becomes a latency problem: the caller's connection is held, the pool is held behind it, and the agent has no signal to back off. Every wait here has a deadline and every deadline resolves to a refusal that says `retry_after_seconds`.
- **Per-tool-name semaphores.** More knobs, no more protection: the scarce resources are the embedding provider, HNSW/pool time, and the indexer. Three classes name exactly those.
- **Refunding a slot on a failed body / refunding a token on a refusal.** Rejected for #162's stated reason in both directions: a tool that always fails would be free.
- **Enforcing the query cap inside the search bodies.** D9 — it would be a post-body marker and would pollute the percentiles.

## Risks / Trade-offs

- **Shared egress IPs and the failed-auth budget.** claude.ai's MCP client egresses from shared addresses, so one tenant's broken client could spend another's failure budget and both would see 429 for up to the window. Mitigated by a deliberately generous default (60 failures / 5 min — no working client fails 60 times in 5 minutes), by `MCP_AUTH_FAILURE_LIMIT=null` as an operator escape hatch, and by one WARNING naming the IP the first time the budget engages so the state is diagnosable rather than mysterious. **Declared, not closed.**
- **One principal can still occupy the `embedding` class briefly.** With `MCP_MAX_CONCURRENT_EMBEDDING_PER_PRINCIPAL = 1` a principal holds at most one of the two slots, so a second principal always has one — that is the fairness guarantee. Two *different* principals can still make a third wait up to the 5 s budget and then be refused. That is the honest outcome for a resource the provider serialises anyway, not a defect.
- **A shared key is a shared bucket.** Two agents on one API key contend with each other, exactly as they do for the daily quota. Same answer as #162: an agent that deserves isolation deserves its own credential, and the keys page is where that is made.
- **The defaults are guesses against a small sample.** Production traffic is low enough (~1,600 calls/30 days) that no default derived from it is stress-tested. Every one is a setting, the refusals are counted per tool on `/admin/performance`, and the first week after deploy should be read there before treating any number as settled.
- **A new gate on the hottest path in the server.** Mitigated by D6 (no I/O, no lock, no await) and pinned by a statement-counting test, which is the only way this regresses invisibly.
- **`--workers 1` becomes load-bearing.** D7. Recorded in the Dockerfile, the architecture note and the spec.
- **The new-key default can surprise an operator** who creates a key and later hits 5,000. The refusal already names the limit and points at the control panel (#162), the keys page shows consumption, and the form states the default at creation time.

## Migration Plan

None. No schema change, no backfill, no new dependency. `make test-schema` is not triggered by this change; `make db-check` still runs after deploy as usual. Rollback is a redeploy of the previous image — the settings are read at boot and nothing is persisted. Every control can also be turned off in `.env` without a code change: null the two nullable settings, raise the concurrency numbers, and null `DEFAULT_DAILY_REQUEST_LIMIT`.

## Open Questions

These are the numbers that want the owner's word; each has a recommendation and none blocks drafting.

1. **`MCP_RATE_LIMIT_PER_MINUTE` / `MCP_RATE_LIMIT_BURST` — 120 / 30?** Recommended. 120/min is far above any observed usage and still stops a hot loop within a second; a burst of 30 covers an agent fanning out reads after a search.
2. **`DEFAULT_DAILY_REQUEST_LIMIT` — 5,000?** Recommended (D12). The alternative worth considering is 2,000, which is still ~40× observed usage and halves a runaway's reach.
3. **`MCP_AUTH_FAILURE_LIMIT` — 60 per 5 minutes?** Recommended, with the shared-egress risk above as the reason it is not lower.
4. **`MCP_MAX_CONCURRENT_TOOL_CALLS` — 12 against a 5 + 10 pool?** Recommended: below the pool so a saturated tool surface still leaves connections for the panel, the indexer and `/health`.
5. **Should existing production keys be given a limit at deploy time?** #194 recommends it. This change deliberately does *not* touch them (grandfathering is the whole point of D12); the operator setting 5,000 on the five live keys is a one-minute panel action and should be a post-deploy task, not a migration.
