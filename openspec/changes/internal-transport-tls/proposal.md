## Why

Two findings from the 2026-09-04 OWASP ASVS 5.0 assessment are about the hops **behind** the TLS edge: the connections this application opens to its own dependencies. Both are verified on the production host, both are medium (exposure is bounded to one Docker host), and both share one property that makes them worse than "unencrypted": **nothing tells the operator.**

- **#184 (V12.3.1) — application → PostgreSQL.** `src/database.py` builds the engine with no `ssl` argument and `DATABASE_URL` carries no TLS parameter, so asyncpg's default `sslmode=prefer` applies. Against a server with `ssl=off`, `prefer` tries TLS, is told no, and **silently** reconnects in cleartext. Every note body the tsvector and embedding writers carry, every API-key and OAuth-token hash lookup, every usage row and session crosses a bridge network shared with unrelated stacks in the clear. `alembic/env.py` builds its own engine from the same URL and shares the path. Codex's audit note adds the correct fix shape: `sslmode=require` alone encrypts but does not authenticate the server, so the strict mode must be a verifying `SSLContext`, and the process must fail at startup if the live session is not encrypted.
- **#185 (V12.3.3) — application → embedding provider** (and Traefik → uvicorn, Traefik → oauth2-proxy). `OllamaProvider` POSTs every chunk and every `semantic_search` / `find_related` query to `OLLAMA_URL`, which is `http://` in production; the control panel's settings page pings the same URL. `OPENAI_BASE_URL` accepts any scheme too, although it is documented to support Azure and OpenAI-compatible gateways that may well be internal. An interposing peer reads every tenant's text and — worse for this product — can return attacker-chosen vectors, i.e. **silently wrong search results an agent will act on.**

The server half of both fixes — turning `ssl` on in a PostgreSQL instance other stacks share, putting Ollama behind TLS, giving uvicorn and oauth2-proxy certificates, Traefik `serversTransport`s — is **host infrastructure owned by the operator**, and none of it is ready. This change is the **application half**: it makes the client side able to *demand* and *verify* TLS on both hops, removes the *silent* part today, and turns strictness into a one-line `.env` change for the day the infrastructure catches up. It must deploy against today's production (Postgres `ssl=off`, Ollama `http://` on a private bridge) without breaking it.

## What Changes

- **Database TLS becomes a setting, with one place to state it.** `DATABASE_SSL_MODE` = `disable | prefer | require | verify-ca | verify-full`, **default `prefer`** (exactly today's behaviour), plus `DATABASE_SSL_CA_FILE` and an optional client `DATABASE_SSL_CERT_FILE` / `DATABASE_SSL_KEY_FILE` pair. `require` and `verify-*` are built as an explicit `ssl.SSLContext` (TLS ≥ 1.2; `verify-ca` requires the chain; `verify-full` also checks the hostname), which asyncpg treats as mandatory TLS with **no** plaintext retry. One helper supplies these `connect_args` to **every production connection creator**: `src/database.py`'s engine (which the lifespan, the MCP stdio entry point and both maintenance scripts share) and `alembic/env.py`'s migration engine.
- **Boot-time refusal of every ambiguous TLS configuration.** A TLS key already present in `DATABASE_URL`'s query (`ssl`, `sslmode`, `sslrootcert`, …) is refused — SQLAlchemy would pass it to asyncpg and then silently let `connect_args` override it. A `PGSSL*` environment variable is refused for the same reason. A CA file with a non-verifying mode, a verifying mode without a CA file, an unreadable or unparseable CA file, and half a client-certificate pair are all refused at settings construction.
- **A startup transport assertion**, in the lifespan beside `_check_embedding_dim` and before it: read `pg_stat_ssl` for the application's own backend. Under `require` / `verify-*` a plaintext (or unreadable) session, or a connection the server refused, **exits the process**. Under `prefer` / `disable` a plaintext session emits one catalogued `internal_transport_plaintext` security event naming the hop. The effective transport state of every hop is logged once at startup.
- **An embedding endpoint scheme policy**, applied to the **active** provider's URL (`OLLAMA_URL` or `OPENAI_BASE_URL`) at settings construction: `https` accepted; `http` to a literal loopback host accepted; `http` to anything else **refused unless `EMBEDDING_ALLOW_PLAINTEXT=true`**, which then emits the same catalogued event at startup. Any other scheme, a missing host, or userinfo in the URL is refused outright. `EMBEDDING_CA_FILE` pins the trust anchor for an internal CA. One client factory builds **every** HTTP client that talks to those URLs — both providers and the panel's Ollama reachability ping — so the policy, the CA and `follow_redirects=False` cannot diverge between call sites.
- **`MCP_SANDBOX_MODE` keeps working**: it skips the embedding scheme refusal (it never calls a provider) and the lifespan's database probe (it has no database), as it already skips the dimension and fingerprint guards.
- **BREAKING (operator, one line):** a deployment whose active embedding URL is `http://` to a non-loopback host — including the default `http://ollama:11434` — refuses to boot until `EMBEDDING_ALLOW_PLAINTEXT=true` is added to its `.env`. `.env.example` ships the line beside the `http://` default so a fresh copy boots. A `DATABASE_URL` carrying a TLS query parameter must move it to `DATABASE_SSL_MODE`. See design D6 for why refusal and not a warning is the default.

No migration, no new dependency, no change to any tool's behaviour or response, and no change to Traefik, uvicorn's listener or the compose healthcheck.

## Capabilities

### New Capabilities

- `internal-transport-security`: the transport the application uses for its own outbound hops — database TLS modes and their verification semantics, the single configuration source and its boot-time conflict refusals, the startup session assertion, the embedding endpoint scheme policy and CA pinning, the single client factory, the startup transport report, and the sandbox exemption.

### Modified Capabilities

- `security-event-logging`: one new catalogued event, `internal_transport_plaintext`, emitted at most once per hop per process start, carrying only `reason` (the hop) and `outcome` (the policy that admitted it).

- Deploy: the production deploy-dir `.env` gains `EMBEDDING_ALLOW_PLAINTEXT=true` **before** `make deploy` (task 7.1). `DATABASE_SSL_MODE` stays unset (`prefer`) until the operator enables server-side TLS.

No migration, so `make test-schema` is not required; `make db-check` after deploy regardless.
- Partially addresses #184 and #185: the application half closes; each issue stays open (or is closed in favour of) the infrastructure follow-up issue whose text is in design.md, "Operator follow-up".
