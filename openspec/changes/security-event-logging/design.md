## Context

Single uvicorn worker (`Dockerfile:31`, `--workers 1`), stdout/stderr scraped per line by Alloy into Loki. The panel's health page reads a second, in-process sink: `src/services/error_log.py`'s 100-entry ERROR ring buffer, attached in the lifespan to the root logger **and** to `uvicorn.error`. Those two sinks are the whole observability surface, and both are downstream of one root-logger configuration that never takes effect.

Constraints that shape the fix:

- **The SDK wins the race by construction.** `src/main.py:26` imports `src.mcp_server.server`, whose module-level `FastMCP(...)` (`server.py:91`) calls the SDK's `configure_logging()`, which runs `logging.basicConfig(handlers=[RichHandler(...)], format="%(message)s")`. `basicConfig` is a no-op once the root has a handler, so `src/main.py:32` never applies. Any fix must run **after** that import and must be forceful.
- **The ring buffer is a live feature and must not be collateral damage.** `logging.basicConfig(force=True)` removes *and closes* every existing root handler. Today the ordering happens to save us — `configure_logging()` at import time precedes `error_log.attach()` in the lifespan — but "happens to" is not a guarantee, and the lifespan is re-entered in tests.
- **`extra` is attacker-influenced.** Ten `auth_failure` sites already pass `extra=`, one of them derived from a **presented bearer token** (`_redacted_prefix(token)`, `src/mcp_server/auth.py:57`). A formatter that serialises `record.__dict__` minus the standard keys would ship key prefixes, vault paths and query strings into a structured sink the moment somebody adds a field.
- **The transfer 404 is an anti-oracle.** `src/transfer/routes.py:114` — *"Never add a reason: the reason is the oracle."* Whatever is logged, the response stays byte-identical. And the admission predicates that produce it (`lookup_token`, `claim_upload`) are one filtered query each, deliberately: they are the linearizability argument for single-use redemption.
- **`_tracked` is the only place a tool call is observed**, and `usage_logs` rows are read by `/admin/usage`, `/admin/performance` and `/admin/search-analytics` with **unguarded casts** on reserved `params` keys (`docs/architecture/usage-attribution.md`). A new marker is a schema decision even without a migration.
- **Codex reviewed all four findings** before this proposal was written and attached mandatory caveats: allow-list the extras (#190), reason codes only and never secret material (#191), centralise the permission-denied marker, log a redacted tag plus the trusted client identity, keep responses uniform, rate-limit denial logging (#192), catch `Exception` and not `BaseException`, make the audit write best-effort, re-raise (#193).

**Three pre-code Codex reviews have run against this design.** Round 1 (2 BLOCKER, 11 MAJOR, 4 MINOR) found that the draft promised "exactly one record per outcome" while also promising to suppress records, specified six transfer refusal reasons the code cannot distinguish, wrapped work that is not the tool body in the exception handler, and handed a fresh suppression allowance to every new bogus bearer token. Round 2 (1 BLOCKER, 5 MAJOR, 3 MINOR) found that round 1's own answers were double-checking the suppressor's allowance, losing suppressed counts on eviction, contradicting the field-provenance classes in half the catalogue, leaving INFO unbounded, emitting a success before its commit, and claiming a canary test that cannot cover a server-*generated* secret. Round 3 (6 MAJOR, 3 MINOR, no blocker — the final spec round) found that a failure of round 2's diagnosis read could turn the uniform 404 into a 500, that every *existing* actor-triggerable refusal still bypassed the suppressor entirely, that formatter-owned names were mixed in with call-site fields, that an administrator acting on another user's grant produced one ambiguous `user_id`, and that the draft had miscounted the panel's actor re-check sites. All three rounds are folded in, and the map from finding to decision is the last section of this document.

## Goals / Non-Goals

**Goals:**
- One physical line per record, machine-parseable, UTC-stamped, with the structured fields the code already passes actually present.
- One emission attempt per authentication and authorization outcome, carrying a reason code and identities of a declared, per-event provenance.
- A refused write and a failed tool body are distinguishable from a successful call in `usage_logs` and on `/admin/usage`.
- No new failure mode: logging never raises into a request path, never changes a response, never adds a query to an accepted request, and never masks an exception.
- **Bounded log volume at every level, with the bound accounted for**, so an operator can always tell a quiet period from a suppressed one.

**Non-Goals:**
- **Re-formatting uvicorn's own loggers.** `uvicorn`/`uvicorn.access`/`uvicorn.error` carry their own handlers with `propagate: false` (which is exactly why `error_log` attaches to `uvicorn.error` by name), so their lines stay in uvicorn's format and the container log is mixed JSON and text. Clearing their handlers and letting them propagate would give a uniform stream, but it changes the shape of the highest-volume lines in an existing Loki pipeline for no security benefit. Residual R4.
- **A persistent audit table**, and any retention or shipping policy. `usage_logs` records tool calls; security events go to stdout, and what happens to them after Alloy is an operator concern (Residual R2).
- **Bounding how many security events a caller can *cause*.** This change bounds what reaches the log sink (D7) and nothing else. Admission control — a per-principal request bucket and a failed-authentication budget — is the sibling change **`mcp-rate-limits`** (#188/#194). Residual R2.
- **Lowering `error_log.CAPTURE_LEVEL` to WARNING.** The health page is "recent errors", not "recent refusals"; a credential-stuffing burst would evict every real error from a 100-entry buffer. Auth failures stay WARNING and reach Loki only.
- **Moving the write-permission gate into `_tracked`.** That would make `permission_denied` a *pre-body* refusal with a refusal count on `/admin/performance`, but it also changes quota accounting (a refused write would stop consuming its already-committed slot) and the refusal ordering for nine tools. See D6 and Residual R5.
- **A typed outcome for every in-body tool refusal.** `create_note` on an existing path, a path-validation refusal, a size refusal and a conflict all return an in-band string today and are *not* marked in `usage_logs`; this change does not make them so. See Residual R1.
- **Logging the bare "no `Authorization` header" 401** at `src/mcp_server/auth.py:96`. Unauthenticated probing of `/mcp` is constant background noise with no identity attached; Traefik's access log already counts it.

## Emission: one attempt per outcome, one allowance check, every level bounded

The first draft's requirement was self-contradictory (eleven bad passwords in sixty seconds cannot be both eleven records and at most ten), and round 1's answer — INFO unbounded, WARNING/ERROR suppressed, with a separate `should_emit` for expensive work — left two holes round 2 found: an unauthenticated caller can drive **INFO** records without limit (replaying a signed consent state, a logout, a CSRF-failing form against routes slowapi does not throttle), and a caller that consulted `should_emit` and then called `emit` was charged **twice**, so the flood bound was either doubled or violated depending on which check won.

The contract is therefore:

- **Every outcome in the catalogue SHALL cause exactly one emission attempt** — never zero, never two for one decision, and never one per retry-loop iteration.
- **Every level is suppressed, INFO included** (owner decision, round 2): bounded volume beats audit completeness, because a summary carrying an exact count still tells an operator precisely how many logins succeeded while a quiet log tells them nothing about how many were withheld. Every suppressed record is *counted*; nothing is silently dropped.
- **The allowance is checked exactly once, by acquiring a permit** (D7). `suppressor.acquire(event, subject)` returns a `Permit` or `None`; `emit(permit, ...)` consumes it **without re-checking**. The convenience form `emit(event, subject=…, **fields)` is `acquire` followed by consume, and is what almost every call site uses; the permit form exists for the one call site that must do work to build its fields (the transfer diagnosis, D8).
- **The `usage_logs` row is not a log record and is never suppressed.** A refused or failed tool call always writes its row.

Tests assert the acquire-call count per outcome (with the suppressor forced open), and the sink behaviour under a flood separately.

## The event catalogue

Every record is emitted by `security_events.emit(...)`, whose message is the event name and whose fields are allow-listed (D2) **per event** (D15). Four fields are always present and are not repeated in the table: `ts`, `level`, `logger`, `msg` (the event name). `client_ip` is listed per event rather than assumed: it appears on the events below that name it, always as `request.client.host` **after** `ProxyHeadersMiddleware` (D3). The MCP tool events (`tool_write_refused`, `tool_exception`) **omit it**, because `_tracked` and `_require_write` run below the middleware and no request object or ContextVar carries it there; binding one is out of scope (Residual R8). **Every field is optional**: a field whose value is not available on the path that emitted the record is absent, and absence is meaningful. A `_submitted` suffix marks a field carrying a value the caller supplied that did **not** resolve to a row (D15). Success records are emitted **after the transaction that makes them true has committed** (D17). Line numbers are the current tree.

**Where the line is drawn.** A site migrates when a caller can trigger it repeatedly, on demand, through a request. Everything driven by the indexer, the embed pass, `vault_fs` housekeeping and startup — `src/services/indexer.py`, `src/services/embeddings.py`, `src/services/vault_fs.py`, `src/services/transfer.py`'s descriptor-close warning, and `src/services/vault.py:1826`'s post-publish flush note — stays on the bare logger: those are background or once-per-pass, they are not refusals, and suppressing them would hide the one class of error the health page exists to show. The migrated set is exactly the table above, and a test asserts no *new* `logger.warning`/`logger.error` call appears in the four request-path modules (`mcp_server/auth.py`, `mcp_server/tools.py`, `transfer/routes.py`, `control_panel/routes.py`) outside it.

**The table is the registry.** `EVENT_FIELDS: dict[str, frozenset[str]]` in `security_events.py` mirrors it, one entry per event. `emit` drops a field the event does not declare, and under the test suite's strict flag it raises instead, so the catalogue and the code cannot drift (D15).

## Decisions

**D1 — Reconfigure the root logger explicitly, after the SDK import, preserving handlers `error_log` owns.**
`src/logging_setup.py` exposes `configure_logging(level=..., fmt=...)`. It walks `logging.getLogger().handlers`, removes and closes every handler **except** the instance `error_log.installed_handler()` returns, installs one `StreamHandler(sys.stderr)` carrying the formatter of D2, sets the root level from `LOG_LEVEL` (default `INFO`), re-applies the existing `httpx`/`httpcore` `WARNING` floors, and is idempotent. `src/main.py` calls it immediately after the import block (replacing the `basicConfig` at `:32`); `src/mcp_stdio.py` calls it with `WARNING` — **stderr matters there**, because stdout is the MCP protocol channel.
*Why not `logging.basicConfig(force=True, handlers=[...])`, which is what #190 recommends:* `force=True` removes **and closes** every root handler, including the ring buffer's, so its safety would depend on `configure_logging()` always running before `error_log.attach()`. It does today (import time versus lifespan) and it must not have to. The explicit loop is the same effect with the exception written down, and it makes "the health page keeps working" a property of the code rather than of an import order. `error_log.attach()` stays idempotent and re-attaching after a reconfiguration is a no-op, so either order is safe.
*Verification:* an in-process integration test that imports `src.main` in a **subprocess**, emits a record carrying `extra`, and asserts on the captured stderr that the root has exactly one non-ring handler, that the line parses as JSON, that `ts` ends in `Z` and parses as UTC, and that the extra field is present — the "actual-process integration test" Codex asked for on #190. A unit test attaches the ring handler first, calls `configure_logging()`, and asserts the buffer still receives an ERROR.

**D2 — A typed, bounded field allow-list; unknown keys are dropped and mistyped values are dropped, never converted.**
The formatter builds its object from `ts` (UTC ISO-8601, milliseconds, `Z`), `level`, `logger`, `msg` (the rendered message, bounded — D16), plus `stack` when `exc_info` is set (D16) and `error_type` derived from the exception class. Then, and only then, it copies the record's `extra` keys that appear in `ALLOWED_FIELDS`, checking each against its declared type and truncating strings to their declared bound:

`reason`(str 64), `outcome`(str 16), `route`(str 200), `method`(str 8), `status`(int), `tool`(str 100), `user_id`(int), `actor_user_id`(int), `username`(str 64), `username_submitted`(str 64), `username_session`(str 64), `user_id_session`(int), `actor_username`(str 64), `actor_kind`(str 20), `key_id`(int), `oauth_token_id`(int), `client_id`(str 64), `client_id_submitted`(str 64), `client_name_submitted`(str 64), `grant_id`(str 64), `scope`(str 64), `token_tag`(str 16), `client_ip`(str 45), `error_type`(str 100), `limit`(int), `limit_count`(int), `count`(int), `day`(str 10), `window_seconds`(int), `duration_ms`(int), `cleared_user_id`(bool), `revoked_tokens`(int).

**A value that does not match its declared type is dropped — the field is omitted — and is never converted to another type.** `user_id="not-an-int"` yields a record with no `user_id`, not a record whose `user_id` is a string: a reader that has to ask "is this integer field an integer today?" cannot query the field at all, and a silent type change is how a Loki dashboard starts lying. Truncation of an over-long *string* is not a type change and stays. The check never raises; a formatting failure degrades to the record's message alone rather than to an exception inside a logging call.
`key_prefix` is **removed from the allow-list**: the name invites logging a raw `omcp_` prefix of a *presented* token, and dropping the field is a safer failure than shipping it. Nothing free-text is allow-listed except `reason` (a closed vocabulary per event, not a message). `error` (a bare `str(exc)`) is *not* a field; the three existing sites move to `error_type`. Query strings, request bodies and note contents have no field to ride in — `route` is `request.url.path` only.
*Alternative rejected:* serialising the whole `extra` dict (the shortest reading of #190's "the record's extra dict"). It is one careless `extra={"path": path}` away from putting one tenant's vault paths into a shared sink.
*Alternative rejected:* logfmt. A value containing a space or a quote needs escaping rules that every consumer must agree on; JSON already has them, and Alloy/Loki parse it natively.
`LOG_FORMAT=text` produces the same allow-listed fields as `ts level logger msg k=v …` on one line, for local `make logs` reading. It is a rendering of the same object, never a second field policy.

**D18 — Three disjoint name spaces: formatter-owned, emitter control, and fields.**
Round 3 found `stack` sitting in the same list as the call-site fields although no call site may pass it, and the emitter's own keywords (`subject`, `level`, `exc_info`, the permit) being indistinguishable from data. Three declarations, disjoint by construction and asserted so by a test:
- **`FORMATTER_OWNED = {ts, level, logger, msg, stack}`** — produced by the formatter from the `LogRecord` itself. A call site that passes one of these as a field has it **dropped** (strict-raises under test): a caller cannot forge a timestamp, a level or a traceback.
- **`EMITTER_CONTROL = {permit, event, subject, level, exc_info}`** — consumed by `emit`/`acquire` and never rendered as data. (`level` appears in both: it is a control keyword the formatter renders from the record, never a field.)
- **`ALLOWED_FIELDS`** — everything a call site may pass, the list in D2. `error_type` is the one dual name: the formatter derives it when `exc_info` is set, and a call site may pass it otherwise; when both are present **the exception wins**, which is stated in the module and tested.
The `EVENT_FIELDS ⊆ ALLOWED_FIELDS` test and the AST sweep's field-key collection both **exclude `EMITTER_CONTROL`** (a `subject=` keyword is not a field to police) and both **reject `FORMATTER_OWNED`** wherever a call site passes it.

**D19 — `actor_user_id` is who acted; `user_id` is who the record is about.**
Round 3's case: an administrator revoking another user's OAuth grant from the panel produced a record with one `user_id` and no way to tell whose it was. `owner_user_id` is **removed** and the pair is fixed for every event:
- **`user_id`** — the account the record is *about*: the login subject, the grant's owner, the target of a password reset, the owner of the client or key a refusal concerned.
- **`actor_user_id`** (with `actor_username` where a name helps) — the authenticated principal that *caused* the record. It is emitted on every surface where one account can act on another's resource — panel user administration, the OAuth grant/client/token administration pages, key administration, and the cross-user refusals — **including when the two are equal** (an admin editing their own account), so a query for "everything this administrator did" is complete rather than silently missing self-actions.
- On surfaces where the subject *is* the actor (login, logout, consent, a token exchange, an MCP tool call) only `user_id` is emitted; adding a duplicate would double every routine record for nothing.
- `/revoke` is authenticated as the *client*, not as a person, so it emits `user_id` (the grant's owner) and **no** `actor_user_id`. The panel path emits both. A test revokes user B's grant as admin A and asserts `actor_user_id = A`, `user_id = B`.
These are distinct from `actor_kind`, which describes the *kind* of credential an MCP call arrived on and is unrelated to a human principal. (`actor_ref`, its companion in `usage_logs`, is **not** a log field — D20.)

**D15 — Provenance is a property of the (event, field) pair, expressed in the field name and enforced by a per-event registry.**
Round 1 declared a global class per field. Round 2 showed that contradicts half the catalogue: a *successful* login logs a username that did resolve, a failed one logs a username that did not; a successful token exchange logs a `client_id` from a row, an unknown-client refusal logs one from the form; DCR logs a client-supplied name; and the early refresh failures have no `grant_id` at all. So:
- **Where a field appears in both roles, the name carries the role.** `username` / `username_submitted`, `client_id` / `client_id_submitted`. The unsuffixed name is **resolved**: it may hold only a value read from a database row. The `_submitted` name is caller-supplied, truncated, and — crucially — **never a suppression subject** (D7). `client_name_submitted` has no resolved twin: it is always the client's own text.
- **Always-resolved fields** may never hold a caller-supplied value: `user_id`, `actor_user_id`, `actor_username`, `key_id`, `oauth_token_id`, `grant_id`, `actor_kind`, `scope`. **Session-derived fields** are a third provenance, marked `_session`: `user_id_session` and `username_session` are copied from the session cookie without a database read, so they may name an account that has since been renamed or deleted — which is exactly what a logout record can honestly say (D19's `user_id` would require a lookup the logout path deliberately does not perform). `key_id` is an `api_keys.id` and nothing else — the OAuth branches of `auth_failure` move their `oauth_tokens.id` to `oauth_token_id`, which is the field that names it in `usage_logs` too.
- **`token_tag` is derived**: `"sha:" + sha256(value).hexdigest()[:8]`, `_redacted_prefix`'s exact behaviour, moved into `src/services/security_events.py` as `redacted_token_tag()` with `src/mcp_server/auth.py` delegating to it, so there is one definition and one test. A presented credential may reach the log **in no other form**. When no token was presented the field is **absent** — not `"sha:"` of the empty string, which would be a constant that reads like a tag.
- **Every field is optional, and error paths are expected to carry fewer.** `EVENT_FIELDS` declares the *permitted* set per event, not a required one; a record missing a field means the emitting path did not have it. The catalogue's Fields column says which are conditional and on what.
- **Enforcement.** `emit` drops any field the event does not declare (and raises under the test suite's strict flag), so a call site cannot quietly widen an event. The AST sweep (D14) additionally rejects any field name absent from `ALLOWED_FIELDS`, and a test asserts `EVENT_FIELDS ⊆ ALLOWED_FIELDS` and that every catalogue row has an entry.

**D16 — Messages and tracebacks have their own rule, and the canaries cover generated secrets as well as submitted ones.**
The draft's "no record SHALL contain a request-derived path" was unsatisfiable: `move_note`'s existing warnings interpolate vault paths into `msg`, and any traceback may carry an exception message built from a path. The rule is split:
- **Structured fields** carry no path, no body, no query string and no credential material — enforced by the allow-list, which simply has no field for them.
- **`msg`** is a developer-authored constant or format string. It MAY interpolate operational context, including a vault-relative path, exactly as it does today. It MUST NOT interpolate credential material — a password, secret, code, token, verifier, cookie or CSRF token.
- **`stack`** is present only with `exc_info`, and an exception message is not under this change's control; it is accepted as operational text under the same rule as `msg`.
- **Bounding is head-and-tail, not truncation.** "The whole traceback, bounded at 8 KiB" was a contradiction. `stack` keeps the **first 4 KiB and the last 3 KiB** with an elision marker naming the dropped byte count in between, and the formatter guarantees the exception **type line and the final line survive** — the two lines that identify a fault — by appending them after the tail if elision would have removed them. A traceback under the budget is emitted whole.
- **Two kinds of canary, because half the secrets are not submitted.** A submitted canary is a unique 32-character random value placed in a real credential position: the panel password, the OAuth `client_secret` on `/token` and `/revoke`, the authorization `code`, the `refresh_token`, the PKCE `code_verifier`, the session cookie, the CSRF token, the MCP bearer token, and the **transfer redemption bearer token**. A **generated** canary cannot be planted, so the test **captures the value the server produced** and asserts its absence: the `client_secret` returned by DCR (**not** the `client_id`, which is a public identifier the catalogue logs on purpose), the authorization `code` in the `/authorize` redirect, the `access_token`/`refresh_token` pair from `/token` and from a rotation, the `omcp_` key returned by key creation, and the transfer token inside a minted URL. Every case asserts that no captured record contains the value **or any substring of it 12 characters or longer**, in any field, message or traceback; and that a request carrying no token produces no `token_tag` field at all.

**D3 — The client identity is `request.client.host`, after `ProxyHeadersMiddleware`.**
There is no IP helper in the tree today. `security_events.client_ip(request)` returns `request.client.host` (or `None`), because `ProxyHeadersMiddleware` (`src/main.py:303`) has already rewritten `scope["client"]` from `X-Forwarded-For` **only** for peers inside the RFC 1918 ranges the `request-trust` capability mandates. Reading `X-Forwarded-For` directly would accept a spoofed header from any client — the exact thing that capability exists to prevent — so the helper never touches headers, and a test pins that a forged header from an untrusted peer does not appear in a record.

**D4 — `permission_denied` is recorded once, at `_require_write` itself.**
`_require_write` gains two lines before its return: `timing.record("error", _PERMISSION_DENIED_MARKER)` and one `security_events.emit("tool_write_refused", ...)`. `timing.record` is a no-op outside a tracked call (`src/services/timing.py:72`), so a call from a test or a future non-tool path cannot raise, and `_tracked` merges the holder into `params` at `:733` — which means **all nine call sites** (`create_note`, `edit_note`, `move_note`, `delete_note`, `set_frontmatter`, `write_file`, `delete_file`, and `request_upload` / `import_from_url` through `_mint_preflight`) inherit the marker without being touched. That is Codex's "centralize the marker" caveat; a per-caller marker is eight chances to forget one and a tenth tool that silently has none.
`request_download` calls `_mint_preflight(need_write=False)` and is deliberately unaffected.

**D5 — The exception handler wraps the tool body and nothing else.**
The draft put `except Exception` on `_tracked`'s outer `try`, which spans the three admission gates *and* the whole telemetry tail. That misclassifies two unrelated failures as tool failures: a database fault inside the quota gate (before the body ever ran — and `quotas.admit` already logs `quota_admission_failed` and re-raises deliberately), and a failure in `_truncate_params`/`_log_usage` **after a write has already landed on disk**. Reporting a completed `edit_note` as `tool_exception` is exactly the "silently wrong record" this change exists to prevent.
So the structure is an explicit two-state one, and the body call gets its own `try`:

```
if refusal is not None:
    result = <refusal>                 # no body ran; existing markers apply
else:
    try:
        result = await fn(*args, **kwargs)     # the only guarded expression
    except Exception as exc:
        <duration; emit tool_exception; best-effort row; raise>
# from here the body has COMPLETED; nothing below may write tool_exception
duration_ms = ...; params = ...; await _log_usage(...)
```

The outer `try:`/`finally: timing.clear(token)` is unchanged. The invariant, stated for the reviewer and pinned by a test: **`tool_exception` is written only on the path where `await fn(...)` raised**, and a failure of anything after that expression returns leaves the ordinary success-path row (or, if `_log_usage` itself fails, the existing `Failed to log usage` warning).
`Exception`, never `BaseException`: `asyncio.CancelledError` is a `BaseException` in 3.8+, and a client disconnect or a shutdown must not be recorded as a tool failure or write a row.
Inside the handler, in order: (1) measure `duration_ms` from the same `start`; (2) `emit("tool_exception", level=ERROR, exc_info=exc, …)` — first, because it is the cheapest step and the one the health page depends on; (3) the best-effort row (D11); (4) a bare `raise`, so the SDK still produces its error result and the traceback is unchanged.
The row carries the same `params` the success path builds (bound arguments through `_truncate_params`, then `timing.current()`), with `error = "tool_exception"` and `error_type` merged **over the top**, `duration_ms` as measured and `response_size = 0`. That precedence is deliberate: a body that recorded `related_source_not_found` and *then* raised is logged as `tool_exception`, because the exception is the outcome. `error_type` is a **new reserved `params` key** (string), registered in `docs/architecture/usage-attribution.md`; no reader casts it.
*Alternative rejected:* logging the exception and skipping the row. `/admin/performance` is the view built to find slow paths, and a tool that raises after eight seconds of I/O is the slowest path there is.

**D11 — The audit write reports whether it wrote, and a cancellation during it is deliberately superseded by the tool's exception.**
`_log_usage` swallows every insertion failure internally (its last-resort `except` exists so that logging can never fail a call that already did its work), so the exception handler could not have known whether the row landed. `_log_usage` therefore **returns an explicit status** — `True` when a row was inserted, `False` when it gave up — with its existing behaviour and every existing caller unchanged (the success path ignores the return). The exception handler logs `tool_usage_log_failed` when the status is `False`.
Around the audit `await`, the handler catches **`BaseException`**, deliberately and only there. Round 1 justified this by claiming the runtime re-delivers the cancellation; **that claim was wrong and is withdrawn.** What actually happens is stated plainly: if the enclosing task is cancelled while the audit row is being written, the `CancelledError` is caught, recorded as `tool_usage_log_failed`, and **superseded** — the handler re-raises the tool's original exception instead. The coroutine still unwinds immediately, so cancellation achieves its purpose of stopping the work; what changes is only the exception type the awaiter observes on a call **that had already failed**. The accepted consequence, written down rather than glossed: a `wait_for`/cancel-scope around such a call sees the tool's exception rather than `CancelledError`, so a timeout on a call that was independently failing is reported as that failure. The alternative — letting the cancellation win — loses the tool exception entirely, which is the record this whole change exists to produce. Scoped to a single bookkeeping `await`, and pinned by a test that cancels during the audit and asserts the original exception propagates.

**D6 — Both new markers are post-body, and the pre-body refusal predicate is unchanged.**
`docs/architecture/usage-attribution.md` states the rule: a marker belongs to exactly one side of the body/no-body line, and only pre-body markers belong in `pre_body_refusal_sql()`. `_require_write` is called *inside* a tool body that has already passed the vault gate, the argument screen and the quota gate (and has spent its quota slot); `tool_exception` is by definition a body that ran. Neither is added to `PRE_BODY_REFUSAL_ERROR_MARKERS`; `usage_stats.py` gains only a comment naming them as classified post-body.
*Known cost, accepted:* a read-only credential probing `create_note` five thousand times contributes five thousand near-zero rows to that tool's percentiles. The honest fix is to move the write gate into `_tracked`, which changes quota accounting and refusal order for nine tools. Instead the refusal is made **visible** on `/admin/usage` (D9). Residual R5.

**D7 — One suppressor, one allowance check per outcome, a permit that carries it, and no count lost.**
`security_events` exposes exactly one accounting primitive and two ways to spend it:

```
permit = suppressor.acquire(event, subject)   # -> Permit | None ; charges the allowance once
emit(permit, **fields)                        # consumes it; performs NO further check
emit(event, subject=…, **fields)              # convenience: acquire + consume
```

- **The allowance is charged at `acquire`, exactly once.** Round 1's `should_emit`-then-`emit` shape checked twice — the BLOCKER of round 2 — so `should_emit` is gone. A caller that acquires a permit and then decides not to emit has **spent** its slot; that is the fail-safe direction (it can only make the log quieter, never noisier) and it is stated so callers do not treat acquisition as free.
- **The subject must be computable before any work the permit gates**, because the permit is acquired first. Concretely: `user_id` when the request already resolved a credential to one (every `_tracked` event and every panel event has this), otherwise the **trusted client IP** (D3), otherwise `-`. Round 2 is right that a collapsed transfer refusal cannot use the token's owner: the owner is knowable only *after* the diagnosis the permit gates. **`transfer_refused` therefore always uses the client IP as its subject**, even on the branches where a row later resolves and the record ends up carrying `user_id`. The subject is an accounting key, not an attribution.
- **Shared IPs share an allowance, and that is accepted.** Every transfer redemption arrives through Traefik, so the peer address is the proxy's and `ProxyHeadersMiddleware` rewrites it to the real client's — but two tenants genuinely behind one NAT do share one bucket, so a noisy neighbour can suppress a co-located tenant's *records*. It cannot affect that tenant's responses, their `usage_logs` rows, or their ability to redeem; and the summary states the withheld count, so the operator sees that suppression happened rather than silence. The alternative (per-token subjects) is exactly the unbounded-allowance hole round 1's review closed.
- **Caller-supplied values are never subjects**: `token_tag`, `username_submitted`, `client_id_submitted`. Rotating credentials cannot mint allowances.
- **Two caps.** Per `(event, subject)`: `MAX_EVENTS_PER_WINDOW` = 10 per 60 s. Per `subject` across all events: `MAX_EVENTS_PER_SUBJECT_PER_WINDOW` = 50 per 60 s, so a source cycling through twenty different refusal events cannot multiply its allowance by twenty.
- **Every level is accounted, INFO included** (owner decision, round 2). Unauthenticated INFO paths — replaying a signed consent state, a logout, a CSRF-failing form — are otherwise unbounded on routes slowapi does not throttle.
- **Summaries are emitted lazily, bypass suppression, and are never lost.** A window's `events_suppressed` is emitted when the next `acquire` for that key arrives after the window closed; **when an entry with a nonzero suppressed count is evicted, its summary is emitted first**, before the entry goes (round 2's MAJOR — otherwise the count vanishes and the log silently under-reports); and any window still holding a nonzero count is flushed at shutdown (a lifespan hook, and `atexit` for the stdio entry point). No timer task. A summary carries the suppressed event's own level so an operator filtering at WARNING still sees that warnings were withheld, is never itself suppressed, and never counts against either cap.
- **Bounded and safe.** At most 512 `(event, subject)` keys plus 512 subject keys, evicted **least-recently-used** — every `acquire` moves its key to the end of an `OrderedDict` and eviction pops from the front, so what goes is the key nobody has touched for longest, which is *not* the same as the oldest window (a key acquired steadily keeps a fresh window and never reaches the front). The guarantee is unchanged: **an entry holding a nonzero withheld count emits its summary before it is evicted**; a `threading.Lock` guards both maps; `acquire` catches everything internally and **fails open** — an internal error returns a permit, so the record is emitted; it never drops silently and never raises into a request path.

**D20 — No security record carries a substring of a credential; the engine hides bound parameters.**
Post-implementation adversarial review found two ways one still could. (a) `actor_ref` is `api_keys.key_prefix` for an API-key caller — the first twelve characters of the live key — and `tool_write_refused`/`tool_exception` emitted it, one of them beside a traceback. It is **removed from `ALLOWED_FIELDS`**; those events name the credential by row id (`key_id`, `oauth_token_id`) instead, which answers the same operator question. `usage_logs.actor_ref` is unchanged: that is the #77 attribution design, those rows are read behind the panel's own authentication, and re-shaping them is out of scope here. (b) SQLAlchemy renders a failing statement's **bound parameters** into `StatementError.__str__`, and the API-key lookup, the OAuth-token lookup, the transfer admission, DCR, the authorization-code exchange and the refresh rotation each bind a credential *hash*; a pool or statement timeout on any of them put that hash into any record carrying `exc_info`, and into the health page's ring buffer. `src/database.py` sets **`hide_parameters=True`** — a security setting, written down as one — and the two catalogue events that sit on a credential-bound *write* (`oauth_token_rotation_failed`, `oauth_refresh_reuse_revocation_failed`) are class-only, with no `exc_info` at all.
The three `_submitted` names are the deliberate exception and are **kept**, each bounded at 64 characters: an operator watching a credential-stuffing burst has to see what was tried. The accepted limitation is written down rather than mitigated away — a caller who pastes a live credential into a username, a client-id or a client-name field has up to 64 characters of it logged.

**D21 — The post-body telemetry tail is failure-isolated, not merely unclassified.**
D5 keeps the tail outside the exception classifier so a failed audit is never *reported* as a tool failure. Review found that it was still *being* one: `named_params()` runs each tool's `transforms`, `_response_size` serialises the result, and `_log_usage` takes a pooled connection, so any of the three can raise after `edit_note` has already written the bytes — and the caller then sees an error for a write that stood, which is the same wrong answer from the other side. The tail gets its own best-effort `except Exception`, emits **`tool_telemetry_failed`** (class only — a `transforms` or serialisation failure quotes arguments and results, which are note content and vault paths), and **returns the completed result**. It stays structurally separate from `tool_exception`: an operator filtering for failed calls must not find a call that succeeded. `BaseException` is deliberately not caught — a cancellation is a client that went away, and it keeps unwinding.

**D22 — Releasing a claim is bookkeeping and may not change a decided response.**
`POST /transfer/upload` releases a claimed token back to `pending` on every refusal path — the three re-validation failures, the filesystem refusals, and `PrePublishAborted`, which releases and *then* emits `transfer_refused`. `release_claim` is one conditional UPDATE, but it takes a pooled connection: an exhausted pool turned the fixed 404 into a 500 and lost the refusal record, so the caller learned more from the failure than from the refusal — precisely what the uniform 404 exists to prevent. Release is therefore best-effort and response-neutral (`_release_quietly`), records **`transfer_claim_release_failed`** class-only, and leaves the claim standing until its TTL. That is the safe direction and the same disposition `PostPublishFailure` already takes: a token that stays claimed refuses, it does not over-permit.

**D23 — D18's line is a property of the *call site*, not of the directory it sits in; the guard follows the sites.**
Round 2 found three records that reached the sink unbounded, and all three arrived the same way: a sibling change added a call to a module the sweep did not cover. The lesson is not "add three exemptions" — it is that "request-path module" was the wrong unit.
- **`src/services/transfer.py`'s `owner_quarantined`** (from #199/#234) logged two `logger.warning` lines from a service helper on the redemption path, which an unauthenticated caller replaying one dead capability drives as fast as it can open connections. It is worse than an unbounded duplicate: the *bounded* record beside it called the same condition `root_reassigned`, because that is what the route's predicate collapses to. The fix names the condition instead — `quarantine_refusal` returns `owner_quarantined` or `root_unverified` and logs nothing, `root_refusal(row)` wraps it as a `TransferRefusal`, and the reason reaches the log only through `transfer_refused`. `resolve_root_ok` is untouched, so the accepted-token set does not move and the 404 stays byte-identical: this is D8's diagnosis-after-the-decision shape, applied to the root check. The two codes stay apart because they mean opposite things — one says a tenant's root is shared or unverifiable, the other says *this process* has not finished looking. The operator detail that used to be interpolated into the message lives on the surfaces built for it (#199's panel strip, the user's `indexer_runs` row, and `vault_overlap._log_snapshot`'s once-per-pass ERROR); a structured field for it would be free text on a shared sink.
- **`src/auth/session.py`'s `touch_session`** (from #198) logged one WARNING per failed `last_seen_at` write. The touch interval gates the *write*, and a failing write records no new `last_seen_at` to throttle against, so a stale browser on `GET` drives one record per request forever. It becomes `panel_session_touch_failed`, subject the resolved user, `reason` the stage.
- **The post-admission `UnsupportedFilesystem`** in `src/transfer/routes.py` was the opposite failure — a record that should exist and did not. Phase one's probe emits `transfer_refused_unsupported_fs`; `stream_to_vault`'s re-probe took the same 503 in silence, and that is the more interesting occurrence, because it means the filesystem changed **while a write was in flight**.
*So the guard's scope becomes every module a request can reach:* the four request-path modules plus `src/auth/routes.py`, `src/auth/session.py`, `src/control_panel/users.py`, `src/csrf.py`, `src/services/transfer.py` and `src/services/vault_overlap.py`. The last two carry exemptions rather than migrations, because their remaining sites are the background class D18 keeps on the bare logger — a descriptor-close warning, and a detection pass whose entry points are admin-guarded and once-per-action. Every exemption names its call and says why, and the list is asserted, so the next sibling change adds a decision rather than a hole.

**D8 — The transfer refusal reason is diagnosed after the decision, behind the permit, by a read-only helper with a total precedence.**
The draft named six reasons the code cannot distinguish: `lookup_token` (`src/services/transfer.py:619`) and `claim_upload` (`:536`) are each **one filtered query** — hash, direction, `state = pending`, `expires_at > now` — so expired, wrong-direction, claimed, completed and consumed all arrive as the same `None`, and `_load_valid` collapses credential, root and path failures into another. Re-ordering those queries to yield a reason would rewrite the linearizability argument for single-use redemption, which this change must not touch.
So the reason comes from a **diagnosis pass that runs after the refusal decision is already made, and only when the record will actually be emitted**:

```
permit = suppressor.acquire("transfer_refused", subject=client_ip(request))
if permit is not None:
    refusal = await transfer.classify_token_refusal(session, token, direction=…)
    emit(permit, reason=refusal.reason, token_tag=…, …)
return _not_found()
```

- `src/services/transfer.py` gains `classify_token_refusal(session, token, *, direction) -> TransferRefusal`, a **read-only** helper that selects the row **by token hash alone** and applies a **total precedence, in this order**: `unknown_token` (no row for the hash) → `wrong_direction` (row's direction ≠ the endpoint's) → state (`already_claimed` | `already_completed` | `already_consumed`) → `expired` (state is `pending` but `expires_at <= now`) → `claim_lost` (pending, unexpired, right direction — the conditional UPDATE lost a race). Overlapping cases resolve by that order and are tested explicitly: an expired **and** consumed row reports `already_consumed`; an expired row of the wrong direction reports `wrong_direction`. `TransferRefusal` is a frozen dataclass of `(reason: str, row: TransferToken | None)`.
- The branches the route already knows do **not** call it: `missing_token` (no header — and therefore **no `token_tag`** and no query), `credential_invalid`, `root_reassigned`, `path_invalid`, `publication_unsupported`, `prepublish_revalidation_failed`, `file_unreadable`, `fingerprint_mismatch`, `content_changed`. `_load_valid` (`:163-180`) returns `TransferRefusal` instead of bare `None` on the three predicates it evaluates itself, so those three stop collapsing; its accept path still returns the row and no caller's control flow changes.
- **The diagnosis can fail, and a failure may not change the response.** `classify_token_refusal` issues a database read on a path whose whole contract is a fixed 404, so a transient pool exhaustion or a dead connection there must not turn a refusal into a 500. The call is wrapped in its own `try/except Exception` **outside** the admission decision, which has already been taken: on failure the record is emitted best-effort with `reason = "diagnosis_failed"` and `error_type`, and the route returns the same `_not_found()` it would have returned anyway. A test injects a failing diagnosis query and asserts the response is byte-identical to the ordinary refusal and that the record names `diagnosis_failed`.
- **The publish gate keeps one generic sub-reason** (owner decision, round 3). `before_publish()` yields a `GateHandle` exposing only `ok`, so the post-claim gate at `:527` cannot say *which* of revocation, downgrade, reassignment or cascade delete lost the race; it emits `prepublish_revalidation_failed` and nothing finer. **Accepted limitation, with its consequence stated:** for the seconds-long window between claim and publish, an operator cannot tell a key revocation from a root reassignment from the log. Adding a typed cause to `GateHandle` means touching the locked publish gate, which is out of scope here. Residual R9. The *earlier* re-validation at `:391` is different — the route evaluates `resolve_identity_ok`, `resolve_root_ok` and `_path_ok` itself, so those three keep their distinct reasons.
- **The diagnosis is gated by the permit**, so under an enumeration flood the extra read stops with the log record, and an accepted request never issues it at all.
- The external answer is untouched: `_not_found()` and `NOT_FOUND_BODY` are not modified, and a test asserts the response bytes, status and headers are identical across every cause.

**D17 — A success record is emitted after the transaction that makes it true has committed.**
Round 2 caught `panel_bootstrap_admin_created` being emitted after the insert but *before* the commit at `:328`: a commit that then fails leaves a log line asserting an administrator exists who does not. The rule generalises to every success in the catalogue, and the same defect was present at `panel_login_succeeded` (which precedes the `last_login_at` commit at `:186`) and `panel_password_reset`. So: `panel_login_succeeded`, `panel_bootstrap_admin_created`, `panel_password_reset`, `oauth_token_issued`, `oauth_token_refreshed`, `oauth_consent_granted`, `oauth_client_registered` and `oauth_grant_revoked` are emitted **after** their commit and before the response is built. Refusal and failure records have no such constraint — nothing was written. Tests force the commit to raise and assert no success record was emitted.

**D9 — `/admin/usage` selects the raw values and maps the outcome in the route.**
`recent_logs` (`src/services/usage_filters.py:247`) selects **three raw values**: `ul.params->>'error'`, `ul.params->>'error_type'` and `ul.params->>'over_quota'` — the last as **text, never a `::boolean` cast** (`/admin/performance`'s unguarded casts are a standing hazard: one bad row 500s the page for every user until it ages out). The route maps them with explicit precedence — `tool_exception` (rendered *failed*, with `error_type`) beats any other `error` value; any other `error` value renders *refused* with that value as its reason; then `over_quota` equal to the string `true` renders *refused / over_quota*; anything else non-empty, including an `over_quota` value that is neither `true` nor `false`, renders *refused* showing the raw value. Nothing is discarded between SQL and template.

**D10 — The revocation event is emitted by each HTTP caller, after its commit.**
The draft put it inside `revoke_grant_family` (`src/oauth/grants.py:127`), which cannot attribute it: the helper has no request, no client IP and no session user, and it **does not commit** — a record emitted there is a claim about a transaction that may still roll back. It keeps returning its rowcount and stays free of logging. `/revoke` (`src/oauth/routes.py:1003-1004`, Slice B) and the panel's revoke handler (`src/control_panel/routes.py`, Slice D) each emit `oauth_grant_revoked` **after their own commit**, with the identity each has already resolved plus its request context.

**D12 — The panel guards that raise 403 gain the request they need, and `src/api/routes.py` comes with them.**
`require_admin_panel` (`src/control_panel/routes.py:225`) takes no `Request` today, so its 403 has no route, method or IP; it gains `request: Request` as a FastAPI dependency parameter. `_assert_key_owner`, `_assert_oauth_client_owner` and `_assert_oauth_token_owner` are plain helpers and gain a keyword-only `request` argument — and **`_assert_key_owner` is called from `src/api/routes.py:202`**, so that file changes in the same slice or the build breaks. It also carries an **inline duplicate** of the ownership check at `:224-225` (`revoke_key`, `raise HTTPException(403, "Not your key")`); that site emits `panel_forbidden` with `reason=not_your_key` too. `verify_csrf` already has the request and reads `request.session.get("user_id")` for the record.

**D13 — Nothing bounds how many events a caller can cause, and the change says so.**
The draft claimed refusal rows were "already bounded by the quota gate". They are not: `api_keys.daily_request_limit` is NULL by default and OAuth is exempt by construction, so an authenticated read-only client can drive `permission_denied` rows without limit, and unauthenticated transfer refusals never reach the quota gate at all. D7 bounds the **log**; nothing here bounds the **admission**, and no new mechanism is added by this change. That is the sibling change `mcp-rate-limits` (#188/#194). Residual R2, with log retention and shipping named an operator concern.

**D14 — The allow-list sweep is an AST check.**
A regex over `extra={...}` would miss `security_events.emit(...)` keywords entirely and would be defeated by any formatting change. The sweep parses every module under `src/` with `ast`, and for each call whose callee is `logger.<level>`/`logging.<level>` with an `extra=` keyword, or `security_events.emit` (however imported), it collects the field names: the keys of a literal `dict` for `extra=`, and the keyword names for `emit`. A name outside `ALLOWED_FIELDS` fails the test naming file, line and key. **Dynamic expansion fails the test as well** — `extra=some_dict`, `extra={**base, ...}` and `emit(**fields)` are rejected outright, because a field set the sweep cannot read is a field set the allow-list cannot police. Where the sweep can also resolve the event name literal, it checks the field against that event's `EVENT_FIELDS` entry (D15); where it cannot, the runtime registry check and the strict test flag cover it.

## Residuals

- **R1 — In-body tool refusals other than `permission_denied` remain unmarked.** `create_note` on an existing path, path validation, size and conflict refusals return an in-band string and write an ordinary row. A general typed outcome for every tool return is a change of its own.
- **R2 — Nothing bounds event *admission*.** D13. Deferred to `mcp-rate-limits` (#188/#194). Log retention, shipping and Loki cardinality are operator concerns.
- **R3 — Multi-worker.** The suppressor, like the error ring buffer, is per process. Single-worker today (`--workers 1`); under multiple workers each keeps its own counters and the effective per-window cap multiplies by the worker count.
- **R4 — uvicorn's own loggers keep their format**, so the container log is mixed JSON and text (Non-Goals).
- **R5 — `permission_denied` dilutes a write tool's percentiles** (D6), visible on `/admin/usage`.
- **R6 — Shared source addresses share a suppression allowance** (D7). Accepted: it affects records only, never responses or audit rows, and the summary count makes the suppression visible.
- **R7 — `create_user` takes neither the admin guard's lock nor the actor re-check.** Round 3 corrected the draft: `_actor_still_privileged` guards **three** sites (`edit_user_submit`, `delete_user`, `reset_password`), not four. So an administrator demoted while their create-user form was open can still create an account. That is a pre-existing authorization race, not something this change introduces or fixes; it is recorded here and belongs in a change that owns `users.py`'s critical section.
- **R8 — MCP tool events carry no `client_ip`.** `_tracked` and `_require_write` run below the middleware, and nothing binds the request or its address into a ContextVar. `tool_write_refused` and `tool_exception` therefore identify the *credential* (`actor_kind`, `key_id`/`oauth_token_id` — never `actor_ref`, D20) and the user, not the address. `auth_failure` — emitted in the middleware, where the request is in hand — does carry it, which covers the unauthenticated case.
- **R10 — Post-publication filesystem failures stay on the bare logger, unbounded.** `flush_dir_quietly`, `flush_publication_ancestors_quietly`, `_unlink_quietly`, `discard_staged_name` (`src/services/vault_fs.py`), `_flush_target_dirs`' released-root branch (`src/services/vault.py`) and `_close_quietly` (`src/services/transfer.py`) each log a WARNING when the filesystem fails *after* a write has landed. Owner decision, round 3. **The consequence, stated:** an agent writing to a vault whose filesystem is returning `EIO` produces one warning per successful write — and, on the transfer publish path, up to three — with nothing but the write bucket in `mcp-rate-limits` (#188/#194) to bound it. The trade is deliberate: the alternative is threading a new event through the destructive publication path, and the tool result is `success` in every one of these cases, so the record is a durability note rather than a refusal. If the volume ever matters before that bucket lands, the answer is a per-path counter at the flush helpers, not an emission inside the publish.
- **R9 — The publish gate's refusal cause is opaque.** `prepublish_revalidation_failed` covers revocation, downgrade, reassignment and cascade delete alike (D8), so for that window an operator cannot tell them apart. Owner decision, round 3; a typed cause on `GateHandle` is a change against the locked publish gate.

## Risks / Trade-offs

- [The formatter drops a field somebody needed] → the allow-list is enumerated in one module, the AST sweep names the offending file, line and key, and adding a field is a one-line change plus a bound. Failing closed is the point.
- [A mistyped value silently disappears instead of being coerced] → deliberate (D2), and the AST sweep plus the per-event registry make the field set reviewable; a dropped field is visible as an absent key, a converted one is invisible until a query breaks.
- [Suppressing INFO loses audit completeness] → owner decision; every withheld record is counted and the summary carries the exact number, so "how many logins succeeded" is still answerable from the log.
- [A permit is acquired and never spent] → the slot is charged, so the failure direction is a quieter log, never a louder one; the only caller that can do it is the transfer route, and only if the diagnosis raises.
- [Splitting the login failure branch leaks which usernames exist] → only into the **log**; `_render_login(..., status_code=401)` is byte-identical across all three reasons and a test asserts that.
- [The transfer diagnosis query adds a read to a hot refusal path] → it runs only behind an acquired permit (D8), so a flood pays for at most ten reads per subject per minute and an accepted request pays for none.
- [`classify_token_refusal` becomes a second, drifting copy of the admission predicate] → it is explicitly **not** an admission path: it takes no decision, returns no permission, and its reasons are derived from the row's own columns under a total precedence. A test asserts that for every refusal cause the route still returns 404 and that the diagnosis never changes the outcome.
- [Log volume and cost] → every level is bounded by D7's two caps. Admission is unbounded (R2).
- [`configure_logging` runs twice, or in a test that already attached the buffer] → idempotent by construction (D1), and the ring handler is exempt in both directions.
- [A record's `stack` is elided] → head and tail are kept with the type line and the final line guaranteed (D16).
- [`tool_exception` at ERROR fills the 100-entry buffer during a backend outage] → that is the intended signal, and D7 keeps it to ten per minute per subject so other errors survive.
- [Superseding a cancellation changes what a `wait_for` observes] → D11, stated rather than glossed: only on a call that had already failed, and the alternative loses the tool exception.
- [Slowapi's handler signature changes] → the wrapper delegates to `_rate_limit_exceeded_handler` and returns its response unchanged; if the import breaks, the app fails at startup, not at the first 429.
- [A logging call raises inside a request path] → `acquire` and `emit` catch everything internally and fail open; `error_log.emit` is the precedent.

## Migration Plan

**This change claims no migration number. 024 remains unclaimed and is available to whatever needs it next.** `usage_logs.params` is `JSONB` and both markers plus `error_type` ride in it; no DDL, no alembic revision, and `make db-check` must still report "No new upgrade operations detected". Rollback is a code revert — rows already carrying `error: 'tool_exception'` or `'permission_denied'` are read by the existing `params->>'error'` paths as any other post-body marker.
