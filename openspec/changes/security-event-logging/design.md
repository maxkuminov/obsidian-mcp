## Context

Single uvicorn worker (`Dockerfile:31`, `--workers 1`), stdout/stderr scraped per line by Alloy into Loki. The panel's health page reads a second, in-process sink: `src/services/error_log.py`'s 100-entry ERROR ring buffer, attached in the lifespan to the root logger **and** to `uvicorn.error`. Those two sinks are the whole observability surface, and both are downstream of one root-logger configuration that never takes effect.

Constraints that shape the fix:

- **The SDK wins the race by construction.** `src/main.py:26` imports `src.mcp_server.server`, whose module-level `FastMCP(...)` (`server.py:91`) calls the SDK's `configure_logging()`, which runs `logging.basicConfig(handlers=[RichHandler(...)], format="%(message)s")`. `basicConfig` is a no-op once the root has a handler, so `src/main.py:32` never applies. Any fix must run **after** that import and must be forceful.
- **The ring buffer is a live feature and must not be collateral damage.** `logging.basicConfig(force=True)` removes *and closes* every existing root handler. Today the ordering happens to save us — `configure_logging()` at import time precedes `error_log.attach()` in the lifespan — but "happens to" is not a guarantee, and the lifespan is re-entered in tests.
- **`extra` is attacker-influenced.** Ten `auth_failure` sites already pass `extra=`, one of them derived from a **presented bearer token** (`_redacted_prefix(token)`, `src/mcp_server/auth.py:57`). A formatter that serialises `record.__dict__` minus the standard keys would ship key prefixes, vault paths and query strings into a structured sink the moment somebody adds a field.
- **The transfer 404 is an anti-oracle.** `src/transfer/routes.py:114` — *"Never add a reason: the reason is the oracle."* Whatever is logged, the response stays byte-identical.
- **`_tracked` is the only place a tool call is observed**, and `usage_logs` rows are read by `/admin/usage`, `/admin/performance` and `/admin/search-analytics` with **unguarded casts** on reserved `params` keys (`docs/architecture/usage-attribution.md`). A new marker is a schema decision even without a migration.
- **Codex reviewed all four findings** and attached mandatory caveats: allow-list the extras (#190), reason codes only and never secret material (#191), centralise the permission-denied marker, log a redacted tag plus the trusted client identity, keep responses uniform, rate-limit denial logging (#192), catch `Exception` and not `BaseException`, make the audit write best-effort, re-raise (#193). Every one is folded in below and named at its decision.

## Goals / Non-Goals

**Goals:**
- One physical line per record, machine-parseable, UTC-stamped, with the structured fields the code already passes actually present.
- One record per authentication and authorization outcome, carrying a reason code and the identity a resolved database row supplies — and nothing a caller presented.
- A refused write and a failed tool body are distinguishable from a successful call in `usage_logs` and on `/admin/usage`.
- No new failure mode: logging never raises into a request path, never changes a response, and never masks an exception.

**Non-Goals:**
- **Re-formatting uvicorn's own loggers.** `uvicorn`/`uvicorn.access`/`uvicorn.error` carry their own handlers with `propagate: false` (which is exactly why `error_log` attaches to `uvicorn.error` by name), so their lines stay in uvicorn's format and the container log is mixed JSON and text. Clearing their handlers and letting them propagate would give a uniform stream, but it changes the shape of the highest-volume lines in an existing Loki pipeline for no security benefit. Recorded as a residual on #190; see Open Questions.
- **A persistent audit table.** `usage_logs` records tool calls; authentication events go to the log, and the honest boundary for the in-process buffer stays "since this process started" (`error_log.py`). Persisting security events is a separate change with its own retention question.
- **Lowering `error_log.CAPTURE_LEVEL` to WARNING.** The health page is "recent errors", not "recent refusals"; a credential-stuffing burst would evict every real error from a 100-entry buffer. Auth failures stay WARNING and stay in Loki only. Stated on the page's copy is out of scope; the docs note says it.
- **Moving the write-permission gate into `_tracked`.** That would make `permission_denied` a *pre-body* refusal with a refusal count on `/admin/performance`, but it also changes quota accounting (a refused write would stop consuming its already-committed slot) and the refusal ordering for nine tools. See D6 and Open Questions.
- **Logging the bare "no `Authorization` header" 401** at `src/mcp_server/auth.py:96`. Unauthenticated probing of `/mcp` is constant background noise with no identity attached; Traefik's access log already counts it.
- **A `/mcp` rate limiter** (#188/#194) and per-tenant fairness (#202) — separate changes. The suppressor here bounds the *log*, not the request rate.

## Decisions

**D1 — Reconfigure the root logger explicitly, after the SDK import, preserving handlers `error_log` owns.**
`src/logging_setup.py` exposes `configure_logging(level=..., fmt=...)`. It walks `logging.getLogger().handlers`, removes and closes every handler **except** the instance `error_log.installed_handler()` returns, installs one `StreamHandler(sys.stderr)` carrying the formatter of D2, sets the root level from `LOG_LEVEL` (default `INFO`), re-applies the existing `httpx`/`httpcore` `WARNING` floors, and is idempotent. `src/main.py` calls it immediately after the import block (replacing the `basicConfig` at `:32`); `src/mcp_stdio.py` calls it with `WARNING` — **stderr matters there**, because stdout is the MCP protocol channel.
*Why not `logging.basicConfig(force=True, handlers=[...])`, which is what #190 recommends:* `force=True` removes **and closes** every root handler, including the ring buffer's, so its safety would depend on `configure_logging()` always running before `error_log.attach()`. It does today (import time versus lifespan) and it must not have to. The explicit loop is the same effect with the exception written down, and it makes "the health page keeps working" a property of the code rather than of an import order. `error_log.attach()` stays idempotent and re-attaching after a reconfiguration is a no-op, so either order is safe.
*Verification:* an in-process integration test that imports `src.main` in a **subprocess**, emits a record carrying `extra`, and asserts on the captured stderr that the root has exactly one non-ring handler, that the line parses as JSON, that `ts` ends in `Z` and parses as UTC, and that the extra field is present — the "actual-process integration test" Codex asked for on #190. A unit test attaches the ring handler first, calls `configure_logging()`, and asserts the buffer still receives an ERROR.

**D2 — A typed, bounded field allow-list; unknown keys are dropped, and presented credential material is never a field.**
The formatter builds its object from `ts` (UTC ISO-8601, milliseconds, `Z`), `level`, `logger`, `msg` (the rendered message, bounded to 16 KiB), plus `stack` when `exc_info` is set (the formatted traceback, bounded to 8 KiB and JSON-escaped, so a traceback is **one** line and Loki holds it whole) and `error_type` derived from the exception class. Then, and only then, it copies the record's `extra` keys that appear in `ALLOWED_FIELDS`, coercing each to its declared type and truncating to its declared bound:

`reason`(str 64), `outcome`(str 16), `route`(str 200), `method`(str 8), `status`(int), `tool`(str 100), `user_id`(int), `username`(str 64), `owner_user_id`(int), `actor_kind`(str 20), `actor_ref`(str 64), `key_id`(int), `oauth_token_id`(int), `client_id`(str 64), `client_name`(str 120), `grant_id`(str 64), `scope`(str 64), `token_tag`(str 16), `client_ip`(str 45), `error_type`(str 100), `limit`(int), `count`(int), `day`(str 10), `window_seconds`(int), `duration_ms`(int), `cleared_user_id`(bool).

Two rules make the list a security control rather than a style guide, and both are testable:
- **Identifiers come from resolved rows; presented material appears only as `token_tag`.** `token_tag` is `"sha:" + sha256(value).hexdigest()[:8]` — `_redacted_prefix`'s exact behaviour, moved into `src/services/security_events.py` as `redacted_token_tag()` with `src/mcp_server/auth.py` delegating to it, so there is one definition and one test. `key_prefix` is **removed from the allow-list**: the name invites logging a raw `omcp_` prefix of a *presented* token, and dropping the field is a safer failure than shipping it. `actor_ref` stays allowed because it is read from the credential row the middleware already resolved and is rendered in the panel.
- **Nothing free-text is allow-listed except `msg` and `reason`.** `error` (a bare `str(exc)`) is *not* a field; the three existing sites move to `error_type`, and an exception message reaches the log only through `msg` or `stack`, which is where a reader already expects prose. Query strings, request bodies, vault paths and note contents have no field to ride in — `route` is `request.url.path` only.
A test sweeps `src/` for every `logger.*(..., extra={...})` literal and fails on a key outside the allow-list, so the list cannot drift from the call sites.
*Alternative rejected:* serialising the whole `extra` dict (the shortest reading of #190's "the record's extra dict"). It is one careless `extra={"path": path}` away from putting one tenant's vault paths into a shared sink, which is the Codex caveat verbatim.
*Alternative rejected:* logfmt. A value containing a space or a quote needs escaping rules that every consumer must agree on; JSON already has them, and Alloy/Loki parse it natively.
`LOG_FORMAT=text` produces the same allow-listed fields as `ts level logger msg k=v k=v` on one line, for local `make logs` reading. It is a rendering of the same object, never a second field policy.

**D3 — The client identity is `request.client.host`, after `ProxyHeadersMiddleware`.**
There is no IP helper in the tree today. `security_events.client_ip(request)` returns `request.client.host` (or `None`), because `ProxyHeadersMiddleware` (`src/main.py:303`) has already rewritten `scope["client"]` from `X-Forwarded-For` **only** for peers inside the RFC 1918 ranges the `request-trust` capability mandates. Reading `X-Forwarded-For` directly would accept a spoofed header from any client — the exact thing that capability exists to prevent — so the helper never touches headers, and a test pins that a forged header from an untrusted peer does not appear in a record.

**D4 — `permission_denied` is recorded once, at `_require_write` itself.**
`_require_write` gains two lines before its return: `timing.record("error", _PERMISSION_DENIED_MARKER)` and one `security_events.emit("tool_write_refused", ...)`. `timing.record` is a no-op outside a tracked call (`src/services/timing.py:72`), so a call from a test or a future non-tool path cannot raise, and `_tracked` merges the holder into `params` at `:733` — which means **all nine call sites** (`create_note`, `edit_note`, `move_note`, `delete_note`, `set_frontmatter`, `write_file`, `delete_file`, and `request_upload` / `import_from_url` through `_mint_preflight`) inherit the marker without being touched. That is Codex's "centralize the marker" caveat; a per-caller marker is eight chances to forget one and a tenth tool that silently has none.
`request_download` calls `_mint_preflight(need_write=False)` and is deliberately unaffected.

**D5 — `_tracked` catches `Exception`, logs, writes the row best-effort, re-raises.**
The wrapper's `try` at `:665` gains an `except Exception as exc` before the existing `finally`. In order:
1. `duration_ms` from the same `start`.
2. `security_events.emit("tool_exception", level=ERROR, exc_info=exc, tool=..., error_type=type(exc).__name__, ...)` — **first**, because it is the cheapest step and the one the health page depends on.
3. A **best-effort** usage row inside its own `try/except Exception`: the same `params` the success path builds (bound arguments through `_truncate_params`, then `timing.current()`), then `error = "tool_exception"` and `error_type` merged **over the top**, `duration_ms` as measured and `response_size = 0`. If that raises, `tool_usage_log_failed` is logged and the failure is swallowed.
4. `raise` — bare, so the SDK still produces its error result and the traceback is unchanged.
`Exception`, never `BaseException`: `asyncio.CancelledError` is a `BaseException` in 3.8+, and a client disconnect or a shutdown must not be recorded as a tool failure or write a row (Codex's caveat on #193, and its own test).
The marker precedence in step 3 is deliberate: a body that recorded `related_source_not_found` and *then* raised is logged as `tool_exception`, because the exception is the outcome. `error_type` is a **new reserved `params` key** (string) and is registered as such in `docs/architecture/usage-attribution.md`; no reader casts it.
*Alternative rejected:* logging the exception and skipping the row. `/admin/performance` is the view built to find slow paths, and a tool that raises after eight seconds of I/O is the slowest path there is; leaving it out of `usage_logs` keeps it invisible on exactly the page an operator opens for it.

**D6 — Both new markers are post-body, and the pre-body refusal predicate is unchanged.**
`docs/architecture/usage-attribution.md` states the rule: a marker belongs to exactly one side of the body/no-body line, and only pre-body markers belong in `pre_body_refusal_sql()`. `_require_write` is called *inside* a tool body that has already passed the vault gate, the argument screen and the quota gate (and has spent its quota slot); `tool_exception` is by definition a body that ran. Neither is added to `PRE_BODY_REFUSAL_ERROR_MARKERS`; `usage_stats.py` gains only a comment naming them as classified post-body, so the next reader does not have to re-derive it.
*Known cost, accepted:* a read-only credential probing `create_note` five thousand times contributes five thousand near-zero rows to that tool's percentiles, dragging p50 down — the mirror image of the pollution the predicate exists to prevent. The honest fix is to move the write gate into `_tracked` so the refusal is genuinely pre-body, but that changes quota accounting (a refused write stops consuming the slot it consumes today) and the refusal order for nine tools, which is a behaviour change this logging change should not smuggle in. Instead the refusal is made **visible**: `/admin/usage`'s request log gains an outcome column (D8), so the probing is legible on the page. Raised in Open Questions.

**D7 — Denial logging is rate-limited per event and subject; the usage row never is.**
`security_events.emit` consults a process-local suppressor for every WARNING/ERROR event: at most `MAX_EVENTS_PER_WINDOW` (10) records per `(event, subject)` per `SUPPRESSION_WINDOW_SECONDS` (60), where `subject` is the most specific identity present (`user_id`, else `client_id`, else `token_tag`, else `client_ip`, else `-`). Further records in the window are counted; the first record of the next window for that key is preceded by one `events_suppressed` carrying `reason` (the event name) and `count`. The map is bounded (512 keys, oldest window evicted first), guarded by a `threading.Lock`, and `emit` — like `RingBufferHandler.emit` — **cannot raise**: any internal failure falls back to logging the record unsuppressed.
INFO events are not suppressed: every one of them is already bounded by slowapi (`5/minute` login, `10/minute` token, `3/minute` register, `20/minute` revoke) or by a human clicking a panel button.
This is Codex's caveat on #192 and it also protects the 100-entry ring buffer: without it one hostile client's `tool_exception` loop evicts every other error the process has recorded. The suppressor gates the **log record only** — the `usage_logs` row for a refused or failed tool call is always written, because it is the audit trail and it is already bounded by the quota gate.

**D8 — The transfer refusal is logged where the reason still exists, and the response is untouched.**
The reason collapses inside `_load_valid` (`src/transfer/routes.py:163-180`) and inside `claim_upload`; by the time `_not_found()` is called the caller knows which branch it took. Each `_not_found()` site therefore emits `transfer_refused` with its own `reason` before returning the unchanged `JSONResponse(dict(NOT_FOUND_BODY), 404)`. `token_tag` is `redacted_token_tag(token)` — never the token, never a prefix of it — which is what makes a token-enumeration burst correlatable (same token ⇒ same tag) without putting a live capability in Loki. `user_id`/`key_id`/`oauth_token_id` are logged **only** on the branches where a row resolved (`:391, 412, 527, 680, 691, 697`); on the branches where nothing resolved there is nothing to say, and inventing an identity would be worse than omitting one. The mount-boundary and unsupported-filesystem 503s at `:402-412, 546-550` already log and are untouched.
*Explicitly preserved:* the uniform-404 requirement in `openspec/specs/file-transfer/spec.md`. The added spec requirement asserts the response bytes and status are identical across all six refusal causes **while** each produces a distinct `reason` in the log.

**D9 — `/admin/usage` reads the outcome as text, never as a cast.**
`recent_logs` (`src/services/usage_filters.py:247`) adds two selected expressions: `ul.params->>'error'` and `ul.params->>'over_quota' = 'true'`. The second is a **text comparison, not a `::boolean` cast** — `/admin/performance`'s unguarded casts are a standing hazard documented in `docs/architecture/usage-attribution.md` (one bad row 500s the page for every user until it ages out), and a display badge is not worth adding another. The template renders a badge for a non-null marker (`refused`, with the reason code, for `permission_denied`, `no_vault_assigned`, `argument_not_encodable` and `over_quota`; `failed`, with `error_type`, for `tool_exception`) and nothing at all otherwise, so an unrecognised future marker degrades to its raw string rather than to a blank.

**D10 — The panel guards that raise 403 gain the request they need.**
`require_admin_panel` (`src/control_panel/routes.py:225`) takes no `Request` today, so its 403 has no route, method or IP; it gains `request: Request` as a FastAPI dependency parameter. `_assert_key_owner`, `_assert_oauth_client_owner` and `_assert_oauth_token_owner` are plain helpers; each gains an explicit `request` argument at its three-to-five call sites rather than reading a ContextVar. `verify_csrf` already has the request and reads `request.session.get("user_id")` for the record — without depending on `get_current_user`, which it deliberately does not use.

## Risks / Trade-offs

- [The formatter drops a field somebody needed] → the allow-list is enumerated in one module, the sweep test names the offending file and key, and adding a field is a one-line change plus a bound. Failing closed is the point.
- [Splitting the login failure branch leaks which usernames exist] → only into the **log**; `_render_login(..., status_code=401)` is byte-identical across all three reasons and a test asserts that, so the external oracle is unchanged (#191's "keep the existing constant-response behaviour").
- [Log volume and cost] → INFO events are bounded by the existing rate limits; WARNING/ERROR events are bounded by D7. The steady-state addition is a handful of records per authentication, against a vault server handling tens of tool calls a minute.
- [`configure_logging` runs twice, or in a test that already attached the buffer] → idempotent by construction (D1), and the ring handler is exempt in both directions.
- [A record's `stack` is truncated at 8 KiB] → the first frames and the exception line survive, which is what identifies the fault; `make logs` on the container is unchanged for anything longer. The ring buffer keeps only the first line anyway.
- [`tool_exception` at ERROR fills the 100-entry buffer during a backend outage] → that is the intended signal (the health page should say Ollama is down), and D7's suppressor keeps it to ten per minute per subject so other errors survive.
- [The `permission_denied` marker drags a write tool's p50] → D6; accepted, made visible on `/admin/usage`, raised as an Open Question.
- [Slowapi's handler signature changes] → the wrapper delegates to `_rate_limit_exceeded_handler` and returns its response unchanged; if the import breaks, the app fails at startup, not at the first 429.
- [A logging call raises inside a request path] → `security_events.emit` catches everything internally and `logging`'s own handlers already swallow (`error_log.emit` is the precedent). The exception path in `_tracked` is the one that matters most and is covered by its own negative test.

## Migration Plan

None. `usage_logs.params` is `JSONB` and both markers ride in it; migration 024 is left unclaimed for whatever needs it next. Deploy is the ordinary `make deploy`; `alembic check` must still be clean afterwards because nothing touched the schema. Rollback is a code revert — rows already carrying `error: 'tool_exception'` or `'permission_denied'` are read by the existing `params->>'error'` paths as any other post-body marker.

## Open Questions

1. **Should `permission_denied` stay post-body (this design) or should the write gate move into `_tracked` and become a pre-body refusal?** *Recommendation: keep it post-body here.* Moving the gate changes quota accounting and refusal ordering for nine tools, which belongs in its own change; the percentile dilution is visible on `/admin/usage` via D9 and can be measured before deciding.
2. **Should uvicorn's loggers be folded into the JSON stream?** *Recommendation: no, not in this change* (Non-Goals). It would make every line in `docker logs` one JSON object, but it re-shapes the highest-volume lines in an existing Alloy/Loki pipeline. Worth doing deliberately, with the dashboards in front of you.
3. **Should `LOG_FORMAT` default to `text` outside the container?** *Recommendation: no — one default, `json`, everywhere.* `make logs | jq -r '"\(.ts) \(.level) \(.msg)"'` covers the human case, and a format that differs between dev and prod is a format that gets tested in only one of them.
