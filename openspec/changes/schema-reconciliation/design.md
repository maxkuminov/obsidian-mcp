## Context
Live DB: `alembic_version` = 012; the nine columns are nullable; the CHECK from 010 is missing. 010's committed body created it, and Postgres DDL is transactional, so the live DB was either stamped past 010 or the constraint was dropped afterwards — the operator should audit deploy history/DDL privileges (#53), but 013 does not depend on the answer: it verifies and enforces the complete 010 shape. Measured 2026-08-15: 0 NULLs in every affected column, 0 rows violating the CHECK across 16 `oauth_clients`. Fresh throwaway DBs migrated 001→012 have the CHECK but the same nullability drift, so the nullability part is a migration bug, the CHECK part is live-only drift.

## Goals / Non-Goals
Goals: `alembic check` clean on fresh and live DBs; migration idempotent; never silently mutate/drop conflicting rows. Non-goals: changing model definitions; touching `transfer_tokens`.

## Decisions
1. **Backfill-then-SET NOT NULL per column, each guarded.** Use the model's server default for the backfill (`is_active`→true, `used`/`revoked`→false, `created_at`/`indexed_at`→`now()`); on the live DB this is a no-op. Idempotency: `ALTER COLUMN … SET NOT NULL` is idempotent in Postgres.
2. **CHECK constraint: lock, verify data, verify shape, then create/replace.** In the migration's transaction: `SET LOCAL lock_timeout = '10s'`; `LOCK TABLE oauth_clients IN SHARE ROW EXCLUSIVE MODE` (blocks DML, so the offender check cannot race a concurrent insert); `SELECT client_id FROM oauth_clients WHERE NOT (<predicate>)` → any → `raise RuntimeError` listing them (never `DELETE`/`UPDATE`); then resolve the constraint by `pg_constraint` on `conrelid = 'oauth_clients'::regclass AND contype = 'c' AND conname = …`: if absent → `ADD CONSTRAINT` and `COMMENT ON CONSTRAINT … IS 'created by 013_schema_reconciliation'`; if present, compare `pg_get_constraintdef` with the canonical predicate and require `convalidated` — a mismatch (e.g. a same-named `CHECK (true)`) → drop and re-add the exact predicate in the same transaction (data already verified), also commented; a matching validated constraint → no-op. Also verify the other effects 010 promised (`client_secret_hash` nullable; `token_endpoint_auth_method` varchar(32) NOT NULL default `client_secret_post`) and reconcile them the same way, so the whole 010 shape is guaranteed regardless of how the drift happened.
3. **Downgrade** drops the CHECK only if it carries the 013 COMMENT marker (a fresh 001→013 database keeps 010's constraint); leaves NOT NULL. Both paths tested.
3a. **Locks/timeouts documented:** `SET NOT NULL` takes ACCESS EXCLUSIVE and scans the table (no rewrite); `SET LOCAL lock_timeout = '10s'` and `statement_timeout = '60s'` bound the migration so a long-lived transaction makes the deploy fail fast (old container keeps serving) instead of stalling; `usage_logs` (~10k rows) scans in milliseconds.
4. **Gate:** `alembic check` clean is necessary but not sufficient (autogenerate does not compare CHECK predicates), so the integration test also asserts the catalog directly — `pg_constraint` row for `oauth_clients`, `contype='c'`, `convalidated`, `pg_get_constraintdef` equals the canonical predicate, and negative inserts (public client with a secret; confidential without) are rejected — plus the nine columns' `attnotnull`. Idempotence is exercised by `alembic stamp 012` on the reconciled throwaway DB and `upgrade head` again (revision re-runs), not by a second `upgrade head`. Drift simulation: 001→012, drop the CHECK, drop NOT NULL on the nine, insert NULL rows where possible → 013 → assertions; a same-named `CHECK (true)` variant → replaced by the exact predicate; a violating-row variant → loud failure naming the client_id, catalog unchanged; downgrade on fresh (constraint kept) vs drifted (marker → dropped).

## Risks / Trade-offs
- [Live rows violate the CHECK at deploy time] → migration fails loudly before altering anything; deploy aborts (make deploy migrates before recreating the container, so the old container keeps serving). Measured 0 today.
- [SET NOT NULL locks the table] → tables are small; `usage_logs` is the largest (~10k rows) — sub-second.
- [autogenerate still noisy for other reasons] → the test tells us.

## Migration Plan
`make deploy` (migrate step). Post-deploy: `docker exec obsidian-mcp alembic check` → "No new upgrade operations detected."; `pg_constraint` shows the CHECK. Rollback: `alembic downgrade 012` (drops CHECK only).
