## Why

Two findings from the 2026-09-04 ASVS 5.0 assessment and #149's round-4 pass, both on the note-content path, both about a write or an index pass that goes wrong quietly.

- **#205 (ASVS V2.3.4) — there is no caller-visible write precondition.** The `expected=` compare-and-swap in `_atomic_write_at` is server-internal: `edit_note` reads the file inside the call and compares those bytes immediately before the rename, so it covers the tool's own read→publish interval and *structurally cannot* see a change that landed between the agent's `read_note` and its `edit_note`. An agent that reads a note, thinks, and writes back therefore overwrites a concurrent edit — the second key on the same root, or the owner typing in Obsidian on the read-write mount — with no error and no record. The blast radius is the whole note under full replacement and `replace_frontmatter=True`, the addressed region under `append`/`find`/`section`, and the whole file under `write_file(overwrite=True)`, which has no conflict detection **at all**, not even in-call — the raw-byte publish helpers do not even accept `expected=`. `read_note` surfaces no hash, so even a caller who wanted to guard could not. #212 already corrected the `edit_note` docstring that read as if the in-call compare covered the caller's own round trip; the affordance itself is still missing, and lost-update is the failure class `CLAUDE.md` ranks first.
- **#154 — non-finite YAML floats in frontmatter are Python-representable but not JSON.** `_scrub_frontmatter`'s predicate deliberately admits them (its docstring names non-finite floats alongside dates as "renderable, each consumer's own business"), so `x: .nan` reaches every consumer. `read_note`'s JSON view already coerces it — silently, and to Python's spelling `"nan"` rather than the note's own `.nan`. The indexer does not coerce at all: the float goes into the `notes_metadata.frontmatter` JSONB column through SQLAlchemy's default `json.dumps`, which emits the bare tokens `NaN` / `Infinity` / `-Infinity` that PostgreSQL's `jsonb` parser rejects. The expected consequence is the failure shape #126 already cost this project: the batch upsert raises, the pass's single transaction aborts, nothing commits, `content_hash` never advances, and every subsequent tick retries the same fatal batch — indexing dead for that whole owner because of one note. The same function also feeds `_note_title`, so a note titled `.nan` is a second, quieter inconsistency in the same place.

## What Changes

- **One digest, defined once.** `content_hash` is `"sha256:" + hex(SHA-256(complete raw bytes of the file on disk))`, lowercase — no newline translation, no frontmatter stripping, no re-encoding: exactly the bytes `expected=` compares and exactly the digest `vault_fs.fingerprint` already computes. It is deliberately **not** `notes_metadata.content_hash`, which hashes the universal-newline-*translated* text and therefore differs for every CRLF note. Only the canonical `sha256:<64 lowercase hex>` form is accepted as input; anything else is a typed *malformed* refusal, never a mismatch.
- **Reads hand the digest back.** `read_note` gains a `content_hash` field in its structured result — always the **whole file's**, for a section read and a truncated read alike — computed from the same single read that produces the response, never a second one. `read_file` reports it in the header it already emits for base64 results, and gains `hash_only=True`, a metadata-only response (path, size, MIME, hash, no content) so a text file's hash costs no tokens.
- **Writes accept an optional precondition.** `expected_hash` is added to `edit_note` (all four modes, `dry_run` included), `set_frontmatter`, `write_file`, `move_note` (binding the source note's own bytes), `delete_note`, `delete_file` — every path that can destroy content — and to `create_note`, which can never honour it and therefore answers with a typed refusal rather than a protocol-level argument error. **Never required by default** — omitted, every tool behaves exactly as it does today.
- **Refusals are typed, not prose.** They use the caller-visible refusal shape the sibling `mcp-rate-limits` proposal defines (`src/services/refusals.py`, a final line-initial `MCP-REFUSAL {…}` sentinel appended to the prose and carried into structured results through `refusal_result`). This change contributes six codes: `stale_precondition` (carrying the file's **current** hash), `concurrent_write` (the in-call window, so the two windows are distinguishable by code rather than by prose), `no_incumbent`, `malformed_precondition`, `precondition_unavailable` (the incumbent is over the tool's read cap, so no comparison is possible — carrying the cap's name and value), and `precondition_required` — each with `path` and `nothing_written: true`, and none with a retry delay. If `refusals.py` has not landed when this change is implemented, slice A creates it with the identical contract.
- **One precedence, stated once.** Hash **syntax** first (malformed always wins, before any filesystem work), then no-incumbent, then over-cap, then required mode, then the comparison, then the in-call compare at publication.
- **The existing in-call compare stays.** It closes a different window (this call's read → this call's rename) and the two are documented as a pair: the precondition covers the caller's read → this call's read, `expected=` covers the rest. `write_bytes_at` and `write_bytes` gain the `expected=` parameter they never had, and `write_file(overwrite=True)` uses it — but only on calls that supply `expected_hash`; without one it stays the unconditional replace it is documented to be.
- **Every publishing write reports the resulting `content_hash`** — the hash of the bytes it actually published, so `move_note` reports the destination's and, when a link-rewriting move's own rewrite fails after the rename, the *unrewritten* bytes that are really there; the delete tools report none. A write→write chain is then guarded without a re-read.
- **`read_file`'s metadata header stops being forgeable.** It interpolates the path raw, and a vault path may contain a newline — so a filename could inject a `content_hash:` line into the very header this change asks callers to trust. The path is rendered as a quoted JSON string in the base64 header and the `hash_only` result, uniformly.
- **One deployment lever.** `WRITE_PRECONDITION_REQUIRED` (default **false**) makes the guarded tools refuse an unguarded write with `precondition_required`. A per-deployment decision, never a per-call one, and a no-op on deploy.
- **Non-finite frontmatter numbers are coerced at the JSON and title boundaries, not at the parse.** One shared helper renders them as canonical YAML tokens (`.nan`, `.inf`, `-.inf`) whatever the note spelled, used by the indexer's JSONB write, the indexer's title coercion, `vault.read_file`'s title coercion (which `read_note` and the panel share) and the read view — **mapping keys included**, where both paths stringify today. `_sanitize_value`'s two jobs are split so a change made for the column cannot silently re-key titles. The read view discloses the coercion in a **new `metadata_coercions` list** with the reason code `non_finite_float`, sibling to `metadata_omissions`, whose contract is "dropped whole" and does not cover a retained-but-altered value. The parsed mapping keeps the float, so `set_frontmatter` still round-trips `x: .nan` byte-identically.
- **One title rule, named.** The canonical behaviour is the **indexer's** `_note_title` as it stands (including its 512-character bound and its container stringification), adopted by `read_note` and the panel, with the single exception that a non-finite number renders as its YAML token. That aligns three surfaces at the cost of three listed `read_note` changes — a date inside a container, a non-string mapping key, and a title over 512 characters — each with its expected output in the design.

No migration. No new dependencies. One new boolean setting. No change to `notes_metadata.content_hash`'s definition (changing it would invalidate change detection for every CRLF note and re-embed the vault).

## Capabilities

### New Capabilities

(none)

### Modified Capabilities

- `vault-write`: defines the write-precondition digest once and its single accepted input form; every overwrite path accepts an optional `expected_hash` checked immediately after the in-call read; refusals are typed with a closed code set; the tools that cannot honour one accept the argument and refuse it; `WRITE_PRECONDITION_REQUIRED` can make it mandatory per deployment; the in-call `expected=` compare is restated as the second, distinct window; each write reports the hash of what it published.
- `note-read`: `read_note` returns `content_hash` over the whole file in every mode, from the same read that builds the response, never dropped under budget pressure; the structured result gains `metadata_coercions`; the frontmatter JSON view renders non-finite numbers as canonical YAML tokens and reports the coercion there.
- `file-access`: `read_file` carries the hash in the base64 header — whose path field becomes a quoted JSON string so a filename cannot inject a header line — and gains `hash_only`, with argument precedence documented and decided by value; `write_file` honours `expected_hash`, refuses it where there is no incumbent (including an absent path under `overwrite=True`), and reports the resulting hash; `delete_file` honours it in both modes, before the trash rename or the unlink; the raw-byte publish helpers gain `expected=`.
- `index-integrity`: a non-finite frontmatter number is stored as its canonical YAML token — in values and in mapping keys, the first key winning a coercion collision — can never abort an index pass, and titles the note identically in the index, in `read_note` and in the panel under one named rule.
